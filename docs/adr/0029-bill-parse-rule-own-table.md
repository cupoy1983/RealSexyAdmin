# 账单解析规则存独立表，不用字典

快递账单解析规则（Excel 表头列名映射 + 面单费配置）落在独立表 `ecommerce_bill_parse_rule`，而不是复用框架现有的字典数据机制。调研发现字典的 `dict_value` 字段是 `String(255)`，装不下结构化的列名映射 JSON（部分快递公司字段较多时容易逼近或超出上限）；字典管理页面的编辑框是纯文本框，没有任何 JSON 格式校验，录入错误只能等到真正解析账单时才暴雷。这块配置直接决定 `actual_freight`，进而影响结算净利润（ADR-0025），出错发现得越晚代价越大，所以用独立表换取字段级录入校验和迁移版本管理，即使这意味着比复用字典多写约 700-1000 行代码（五件套 + 前端管理页）。

> **列映射字段随 [ADR-0034](./0034-freight-written-onto-suborder-no-match-table.md) 调整，并于 2026-10-20 收紧为「五项全部必填」。** 需要的表头是五项：运单号、账单日期、账单重量、账单其它费用、收件省，**五项全部必填**。**账单店铺名称表头取消**——账单里的店铺与订单店铺本来就没有映射关系，而运费现在直接回写到匹配到的子订单上，店铺是匹配结果的产物而非输入，因此账单行的店铺改为由原件行摊分到的子订单带出（存 `store_id`，不再存原始店铺名）。账单日期与重量成为必需项，是因为出账月与发货月分离后需要行级日期校验账单没串月，而摊分完全按重量进行（ADR-0034），缺重量就无法判异常。
>
> 收件省原先是可选的，现在改为必填，代价是：**解析规则缺这一列就无法导入**——`logistics/schema.py` 的 `receiver_province` 由可选变必填，`generic_parser` 的必需表头由 4 项变 5 项。之所以值得，是因为省份不一致是「重量省份异常」唯一的判定来源；一条规则漏配表头，异常判定会静默失效（全部按省份相符通过），比导入时报错拦住人危险得多。已存在的旧结构规则（如 `yt`）缺 `receiver_province` 映射，需要在解析规则管理里重配一次才能继续用。

> **删除改为无条件物理删除（2026-10-26 决议 Z11=a）。** 这张表落地时留的是框架软删，而 `bill_type` 上挂着**真唯一索引** `ix_ecommerce_bill_parse_rule_bill_type`：幽灵行仍然占着类型名，实测软删之后同类型重建直接 `1062 Duplicate entry`，那家快递就**永久建不回来**。与本 ADR 上一条「旧结构 `yt` 需要重配一次才能继续用」自相矛盾——重配的前提是能再建一条同类型的，而软删把这条路堵死了；配合 ADR-0033 同日新增的门禁（启用规则为空就不许确认批次），一条被软删的规则既建不回来、又让整月批次卡死。
>
> 所以业务层自己下 DELETE，并且**不设「该类型已有账单批次就拒绝删」的前提**：没有任何外键指向这张表，历史账单行早已把列映射与面单费快照固化在自己行上，删规则不会动到任何一笔已入库的钱。前端二次确认弹窗文案写「不可恢复」，语气与账单批次作废（ADR-0033）一致。代价是配错、删错只能重新手工建一遍规则，而重建规则不影响任何一笔已入库的钱。

> **「停用」的边界写清楚（2026-10-27 决议 AB3=甲、AB9=甲）。** 停用这一档原先只被描述成「不参与门禁」，实际代码却挡不住往里写：停用的类型照样能导账单进来、照样能声明零行批次，与门禁只认 `status=0` 的类型自相矛盾。本轮把两个写入口都关严——账单导入对 `status != 0` 当场拒绝，零行批次声明的取规则查询带上 `status=0`。同时确认**停用不影响历史账单算钱**：它只是给人看的记号，不参与任何摊分与利润判断。设计文档 §16.3、§16.9。

> **面单费也必填，但 0 是合法值（2026-10-30 决议 AL 轮，设计文档 §25）。** 上面把五项表头列映射收成全部必填，面单费却一直漏在外：它是规则上的一个价、不来自账单文件，所以不在那五项里。创建用的字段是 `Field(default=Decimal("0"), ge=0)`——不填也算合法请求，落库 `0`，前端弹窗初值也写死 `0`，表单校验里根本没有这一项。而 0 进了算式（原件行 `actual_freight = 面单费 + 其它费用`、整票反推 `Σ其它费用 + 面单费 × 件量`）就等于这一项不存在，**一声不响**：业务方 2026-10-30 报「之前导入测试数据账单的面单费都没算」，查下来就是这条静默路径。本轮改成：新增与修改都必须显式带这一个值（缺字段和 `null` 都拒），不分启用停用，负数与非数字照旧拒，另加两条录入边界——上限 100 元（含）、小数最多两位（界面按两位精度录入、后端拒收超位的值）。
>
> **0 的含义定为「这家快递不收面单费」**（实测中通快运、顺心捷达两条规则就是 0，业务方当日确认这两类快运不收面单费；圆通 1.65/4.00、中通 1.70/4.10 四个数字也当日确认为准）。既然 0 合法，「必填」就只剩一个落点——新建/编辑时必须显式给一个数；导入时**不再设**「面单费必须非零」那道闸，那会把合法的 0 一起拦死。
>
> **为什么不把列改成可空去区分「没配 / 配了 0」**：那是本 ADR 开头选独立表的初衷所在（字段级录入校验），但为这一件事改表不划算——要一次 DDL 迁移、六条存量规则得先定一个含义刷一遍、界面还要多一个「还没配」的状态。代价写清：库里历史那些 `0.00` 从此说不出是哪一种，只能问人。本轮就是把那两条 0 当面向业务方问清的（答：确实不收），因此**零数据订正**——这十条账单行的钱本来就是对的。这也是本表「快照优先」的又一次体现：规则只是以后怎么读，历史账单行带的是当时的价，改规则不回溯。
