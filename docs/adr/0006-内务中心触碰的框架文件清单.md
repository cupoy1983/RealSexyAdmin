`app/core/base_crud.py` 把数据库异常原样抛给客户端：

```python
raise CustomException(msg=f"创建失败: {e!s}")   # :218
raise CustomException(msg=f"更新失败: {e!s}")   # :256
```

响应体里会带出完整 SQL 语句、绑定参数与真实数据值（Admin 那边在
`docs/ecommerce-profit-phase1-design.md:15.9` 有同样的留档）。属框架文件，按硬约定不动。
业务侧能做的是**别去撞它**：

## 五、2026-11-09 12:41 追加（ADR-0016 A3：删除结果透传）

杜总拍板「删除成功后要告知出单结果」。本轮**又动了两个框架文件**，逐条登记：

| 文件 | 改动 | 原因 |
|---|---|---|
| `app/modules/system/user/service.py` | `delete()` 返回类型 `None` → `str`，把 `dismiss_users()` 带回的结算摘要 `summary()` 返回 | 结算单在删除链内部生成，结果必须往外传 |
| `app/modules/system/user/controller.py` | `delete_user_controller()` 接收该字符串，拼进 `SuccessResponse(msg=...)` | 不改 `response_model`（仍 `ResponseSchema[None]`）、不加 data 字段，避免动框架响应结构 |

- **刻意没改**：`response_model`、请求体联合类型、`UserDeleteWithSettlementSchema` 的 import 位置。
  前端 axios 拦截器对成功的非 GET 请求本就会 `ElMessage.success(data.msg)`，
  把摘要放进 `msg` 就能得到 A3 要的「一条轻量消息、不做弹窗」，零前端额外提示代码。
- `dismiss_users()` 返回从 `list[str]` 改为 `tuple[list[str], DismissalSettlementResultSchema]`：
  原 `skipped` 说明调用方一直忽略，保留不删；新增结算摘要作为第二项。
- 与「一-C」的删除接口联合请求体、`delete()` 透传 `settlement_deductions` 属同一条删除链，
  是那次报批的延续，不另开框架改动面；旧 `list[int]` 删除调用仍兼容。
