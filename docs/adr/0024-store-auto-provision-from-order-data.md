# 店铺从订单数据自动建档，不预配映射表

导入订单时，按订单自带的快麦店铺id（Excel「店铺编码」列）自动创建或更新店铺——名称取「店铺全称」、平台取「店铺平台」。因此不再需要预先配置 `kuaimai_shop_id → store_id` 的映射表，也不再有「未映射店铺/挂起」这一状态；键仍是快麦店铺id而非店铺名，因为店铺名会跨平台撞车。代价是当月有订单的新店铺在被分配负责人前不参与间接成本分摊，故结算门禁增加一条：当月有单的店铺必须都已分配负责人，否则挡住结算。

> **店铺不提供删除，只能停用（2026-10-26 决议 AA8，取代同轮 Z10 的「停用并让出快麦 id」）。** 框架的删除是软删，而 `kuaimai_shop_id` 是唯一索引、不认 `is_deleted`：实测软删一家店之后重导它名下的订单，`ensure_store` 找不到可用行就去 INSERT，撞幽灵行 → **整批导入 500**，那一整个月都进不来。Z10 原本选的是「停用 + 把快麦 id 让出来（加后缀腾键）」，但既然界面早就隐藏了删除按钮、这次又明确「暂时不做删除功能」，就没有任何东西需要腾键——于是简化成：**`/store/delete` 一律拒绝并提示改用停用**，权限点 `store:delete` 保留但不接界面，也不去做「停用后释放 id」那套动作。
>
> 两条边界顺带记清，将来别当新发现：
>
> - **停用不影响自动建档取店**：`ensure_store` 只按快麦 id 命中、不看 `status`，命中后仍会按新 Excel 覆盖刷新 `store_name`/`platform`，但**不会把停用自动改回启用**。所以「停用一家还在出单的店」挡不住订单继续归到它名下，它只是列表/筛选上的一个状态。
> - **停用不影响门禁判定**：「当月有单的店铺都要有负责人」这条仍然算它（结算门禁，ADR-0026），停用不等于退出核算。

> **手填的标识字段不许含空格（2026-10-27 决议 AB2，设计文档 §16.1）。** 快麦店铺id、店铺名称、所属平台在**手工**建档/改名时先 trim 再入库，trim 完为空当作没填直接拒绝，撞了别的店的快麦 id 单独报错。界面侧对应输入框禁空格。~~**自动建档这条路径不动**：上面两条边界说的就是 `ensure_store` 按快麦 id 命中与刷新，导入路径沿用既有整形口径，不为一处空格把整份文件拒掉。~~（这一句已被下面的 AF3 推翻，划线保留是为了留下当时的判断。）停用的语义再次确认：**只是标记**，前端选项文案已写明「停用（仅标记，不影响导入与利润计算）」。

> **自动建档与手工建档用同一把尺（2026-10-29 决议 AF3，设计文档 §20.3，推翻上面 AB2 里「自动建档这条路径不动」那句）。** 当年那句「不为一处空格把整份文件拒掉」护的是**首尾空格**，但实现里走的却是另一条更远的路：Excel「店铺全称」「店铺平台」为空时，导入器拿快麦店铺id 冒充店名、拿空串冒充平台建了档，而这两列在模型与库里都是 NOT NULL 且是人工认店、按平台汇总的唯一凭据。于是「店铺编码有、全称/平台空」这一行不再报错，而是安静地生产一条**名字是数字、平台是空**的店铺记录；一家店有没有这种行取决于当月导出，谁都不会发现。
>
> 改法（三条，「不同即覆盖」不动）：
>
> - **不再伪造标识字段**：主订单取的是**该系统订单号第一次出现的那一行**（ADR-0030 的归并口径），那一行缺「店铺全称」或「店铺平台」就**带行号报错、整份不落库**，与「订单商品明细ID不能为空」同一等级。后面的行不重复这道闸：它们的这两列根本不进库，为它们拒掉整份文件等于把拦截面铺到不参与建档的数据上。
> - **`ensure_store` 补 trim**：自动建档路径写入前对店名/平台做与手工建档同一次 `strip()`，比较也用 trim 后的值——否则 `" 旗舰店 "` 每份文件都会被判成「不同」而反复覆盖，而库里带空格的值又永远匹配不上人工输入的那家。
> - **「不同即覆盖」保留**：命中已有店铺时按新 Excel 刷新名称/平台，这条不变，AF3 只补整形与拒绝伪造。
>
> 为什么不选「跳过这一行」：一行订单明细被跳过就意味着它的金额、运费、成本都从当月利润里少一笔，而校验和（Excel「汇总」行）是按全部行算的——跳过行会立刻把校验和对崩，报出「汇总不一致」这种指错方向的话。带行号拒绝整份文件才是可行动的：快麦那一列补上再导一次。
>
> 边界：这道闸只拦**有有效店铺编码**的行（编码为 `0`/空的垃圾行仍按原样跳过，ADR-0030）；2026-10-29 实测现有 30 家店铺 0 条空平台、0 条「店名=编码」、0 条带首尾空格，主订单里也没有空平台——所以 AF3 拦的是以后，不是给已经进来的数据擦屁股。

> **编码 `0` 是一家真店铺，文件里的占位符店名不许覆盖档案（2026-11-03 决议 AN34，业务方原话「改闸，店铺编码可以为0，店铺名称为0的不进行覆盖。要进利润」，设计文档 §26.12 AN33/AN34、§26.13 第 7 条）。** 上面那句边界里的「编码为 `0`…按原样跳过」以及 AN22 把它升级成「`0` 算没填、整份报错」，从这一条起**作废**：`0` 是快麦给「出库单」这类无源单据留的固定编码，业务方会**手工**建一家快麦店铺id=`0` 的店挂上负责人，那些行要照常进利润。三件事：
>
> - **必填闸一个字没动**：编码**空着**照样带行号整份报错（AN21）。撤销的只是「`0` 也当没填」这一句，代码上 `_INVALID_SHOP_CODES` 那个集合与它的分支整块删除，不留空集合当纪念。
> - **`ensure_store` 的「不同即覆盖」加一条例外**：文件「店铺全称」那一格是占位符（`-` / `--` / `/` / `0` / `无` / `暂无`）时**不拿去覆盖**档案里已有的店名——9月那份文件里编码 `0` 的 9 行，店名写的就是字面 `-`，照原规矩每导一次月就把他那家「出库单」改名成 `-`。平台不受影响，照常覆盖（那批写的是 `其它`，是有效值）。
>   **代价（要说给业务方）**：例外只管覆盖，不管新建。如果他**还没**建出编码 `0` 的店，第一次导入这类文件仍然会按文件值新建一条名叫 `-` 的店铺——先手工把店建好再导，这条就走不到。不为这个再加一道「占位符店名且店不存在就报错」，因为那等于把他说要的「要进利润」又挡回门外。
> - **「要进利润」不需要改代码**：这批是 `ERP发货` + 非分销，正常入库、成本照 ADR-0022 从主表取（主编码 `NLPJ`）、已付 0 就是 0，所以它们是**有成本没收入**的行，利润为负——这是业务方要的结果，不是缺陷。运单号为空，因此不参与运费匹配与摊分（ADR-0034 的寻址线是运单号），也不会被「只看缺账单」筛出来（那条判据要求运单号非空）。
>
> 与 AN22 的关系要说清，别读成「那道闸白装了」：AN22 拦的是「**编码这一格是垃圾值**」，当时我们不知道 `0` 有业务含义；现在知道了，于是那一格变成合法值，而 AF3 那条真正防的事——**拿编码冒充店名、拿空串冒充平台**——仍然由必填闸守着。

> **例外的判据改成「店铺编码 `0`」，那家店的店名与平台两格都不许覆盖；NLPJ 定为有意 0 成本（2026-11-08 决议 AP1/AP3，业务方原话「NLPJ就是0成本，对的。」/「编码0的店铺，店铺名和平台做一个例外，拉取时都不变。」，设计文档 §27）。** 上面 AN34 那一块里有两句从这一条起**作废**：
>
> - 第 29 行末尾「**平台不受影响，照常覆盖（那批写的是 `其它`，是有效值）**」——撤销。改成：**命中已有店铺且 `kuaimai_shop_id == "0"` 时，店名与平台两格都不覆盖，直接返回原对象、不发 UPDATE**。理由是他那句口径本身（他没讲为什么，本 ADR 不替他补）。**事实纠正（2026-11-08 回读 AN33 那条实测）**：出库单文件「店铺平台」那一格写的是 `其它`、**不是** `快麦`；档案里那个 `快麦` 是他 2026-11-06 手工建店时自己填的，从来没被文件刷过。所以「照刷」会把档案刷成 `其它`（正好就是 AP4 丙要的那个对齐），「冻住」是把这一格彻底交给人工——两头都是他的口径能成立的样子，代码按冻的那条写。占位符店名那份词表（`-` / `--` / `/` / `0` / `无` / `暂无`）**保留**，继续管别的店；`0` 这家店走它自己的、更宽的一条例外，两条判据是**先后关系**而不是重叠：先看编码是不是 `0`，是则整条覆盖动作都不做；不是才轮到词表管店名、平台照刷。
> - 第 31 行「**有成本没收入**的行，利润为负——这是业务方要的结果」——**「有成本」那一半作废**。那 9 行的主编码是 `NLPJ`，业务方对它的一句话是「**NLPJ就是0成本，对的。**」：这一格的答案是 `0`，不是「还没录」。所以它们既没收入也没成本，**利润贡献是 0 而不是负**；`cost_missing` 一并置 0，不再进「待补充成本」清单。这一填本该是「0 = 有意」这条语义在本仓库的第一例（填之前主表 1744 行里 `cost_price=0` 的行 **0 条**，290 条全是 NULL），SQL 见设计文档 §27.3；**同一天两次收口：先「1不跑」（这份 SQL 业务方定为不执行，未给理由），再 AQ2「NLPJ 的成本先不管了」（不跑脚本、也不手工填价、也不填 0）**，所以库里今天仍是 NULL、那 9 行仍挂在「待补充成本」清单里，这一例停留在「已确认、不做动作」。钱不受影响（NULL 与 0 算出来都是 `0.00`），细节见 §27.5 与 §27.7。
>
> 「拉取时都不变」里的「拉取」指的是**订单建档路径**（`ensure_store`），不是快麦 API 轮询——那条接口实现存在但没接任何入口。新建路径**一个字不改**（AP5「导入为-，我后面会手工修改」）：店还没建时第一次导入仍会按文件值建出一条名叫 `-` 的店，业务方自己认了这个代价，顺序仍是先建店、再导文件。
>
> 档案侧剩一格只能走 SQL：平台在界面上**根本不可编辑**（手工更新的排除集合里有 `platform`），所以在 AP3 冻住之后，编码 `0` 那家店的平台要改就只能改数据库（AP4 丙那份 SQL 他 2026-11-08 定为不跑，见设计文档 §27.5）。这条例外落地之后 `ensure_store` 永远不会再碰那两格，改一次就是永久的。
> **定案（2026-11-08 AQ1，业务方原话「编码0的店铺，就让平台为快麦吧」）**：这一格**就留「快麦」**，AP4 丙「改成 `其它` 与主订单对齐」作废，「恢复平台照刷」那条备选（文件写的其实是 `其它`，下一张新出库单整单新建时会自动带过来）**记下但不采用**。于是「档案 `快麦` / 主订单 `其它`」这个分裂是本 ADR 的**定案状态**而不是待修缺口——订单表那一格一直是「文件怎么说就怎么记」，为一家店破例就是第二把尺，这句没变。以后谁再提「分裂」，指这一条。
