## 一、要解决的问题

考勤月报列表能看到停用 / 软删员工，薪资流程却按「账号启用且未软删」把他们排除（复核报告功能缺陷 4）。
原 ADR-0011 修订 2 的解法是「月中离职保持账号启用到月末、工资条生成后再走离职」，
与实际「人走了就要立刻在 OA 删除」相冲突。改为：删除用户时把该员工的考勤与薪酬单独结算清楚，
结算凭证与考勤历史都留下，两边口径就不打架了。

## 二、记录形态（C3 拍板）

- 与正式工资条**共用 `iac_salary_payslip`**，用现有 `generation_source` 字段新增 `dismissal` 值区分；
  不新建表、不新增字段、**不跑 Alembic**。
- 不用 `status = 3`：`status` 是确认状态（0 未确认 / 1 已确认），`confirm_payslip()` 会把非 1 的行
  改成 1 并给员工发「工资已发放」钉钉通知，结算单会瞬间变成正式工资条、还会给已离职的人发通知。
  两个维度必须正交。

  2026-11-09 追加（杜总）：结算单没有确认流程，**落库那一刻就是终态**，所以落库直接写
  `status = 1`（已确定），同时写 `confirmed_at = generated_at`、`confirmed_id = created_id`，
  表示「由删除操作人落库即生效」。这不是拿 `status` 当类型标志（类型仍只看
  `generation_source`），而是让「终态凭证」在数据层自洽：
  - `confirm_payslip()` 里 `if row.status == 1` 会再挡一次，等于多一道防误确认的硬保险；
  - 钉钉「工资已发放」通知只在 `confirm_payslip()` 真正执行到赋值之后才发，落库不调它，
    所以结算单 status=1 不会误发通知；
  - `status` 的含义统一为「凭证是否已确定」：正式工资条经超管确认后 1，离职结算单落库即 1。
- 金额字段、计算函数全部复用正式工资条（`SalaryService._calculate`），含 ADR-0011 2026-11-09 修订的
  「全勤 `A >= R`、折算基础工资不封顶」。
- **必须连带改的读路径**（否则会重现「锁的问题」）：
  1. `month_generated()` 排除 `dismissal` —— 否则结算单一落库，整月工资条生成、绩效修改、
     每日自动生成都被判成「已生成」而锁死；
  2. `_payslip_conditions()` 默认排除 `dismissal`（正式工资条列表不混入）；
  3. 新增按月份查 `generation_source = dismissal` 的查询，供「查看离职结算单」按钮用；
  4. `confirm_payslip()` 拒绝结算单；
  5. 落库写 `generation_source = "dismissal"`；
  6. 前端正式工资条列表 / 状态标签按类型区分。
- 弹窗里的「离职日期 / 生成人」用现成的 `generated_at`、`created_id` 展示，不新增列。
- ADR-0011 第四节「确认后永久锁定」、ADR-0012「生成后不能重算」只约束正式工资条；结算单按本 ADR 第五节锁定。

## 三、触发与删除流程

- **只有「删除用户（离职联动）」触发**；停用（`UserModel.status = 1`）不触发（A9）：停用可逆，不是离职。
- 前端落在 `user/index.vue` 已有的删除确认链里（`deleteUsersWithDismissConfirm`，已有 4601 二次确认先例）。
  一次删多人时**一张表列出全部待删人员**，逐行填扣款，无绩效奖金的行自动跳过并标注，一次提交（B8）。
  提示语固定显示，不管是否满半个月：「未满半个月无绩效，未满一个月扣除半月绩效！」
  2026-11-09 12:41 修订（杜总 A1 / A2，取代 11:24 的临时理解）：**删除弹窗只用来逐人填那
  一个绩效扣款数，不做结算预览** —— 不展示结算月份、出单标签、预估实发、逐人 messages，
  也不显示「缺月报显式提示」或任何依赖月报数据的说明。弹窗只显示姓名、绩效基准、
  扣款输入框与固定提示语。后端 `POST /internal/salary/dismissal/context` 只返回姓名 /
  绩效基准 / 是否零绩效 / 提示语，不读月报、不算金额、不预判出单；确认删除后由删除链
  实时拉考勤再按第四节规则落库（A1）。两个「登记绩效扣款」弹窗仍不是同一处：本弹窗在
  用户管理页 `user/index.vue`「离职结算」，扣款不写 `iac_salary_performance_entry`；
  薪资绩效 Tab `SalaryPerformanceTab.vue` 的是生成工资条前的全员绩效登记，扣款进绩效表。
  提示语仍只是操作提醒，**不参与任何金额计算**。
  - **「缺月报显式提示」取消**（A2）：它的依据是预览时读到的旧月报，预览取消后依据就没了；
    真正没有月报只有两种情况 —— 员工无考勤组时 `sync_month` 正常跳过（本来就不该出单），
    钉钉接口临时失败时 D1 整批不删并报错写明月份 —— 都有既有处理，不需要事前预告，
    事前预告还会误导。「哪个月没出单」改由删除成功后的结果消息告知（A3，第九节）。
- **离职结算弹窗始终显示、扣款输入框始终可填**，不会因为某个月已有正式工资条就整个不弹
  或把输入框设成只读。管理员只填**一个**绩效扣款数，落到第四节表格指定的那张结算单；
  无绩效奖金的员工行自动跳过并标注（B8）。
- 后端顺序：预检 → 拉取该员工考勤 → 生成结算单 → 钉钉离职 → 软删绑定 → 软删 OA 用户。
  顺序不能颠倒：钉钉离职后 `getcolumnval` 再也取不到离职人员考勤（ADR-0007）。
- **三道闸都不搬**（E1）：不套用绩效登记的「3 日后」「只能上一个自然月」「`month_synced` 全月完成」。
  改为「按月份各自要求该员工该月月报已存在」；实时拉取后仍缺月报的月份不出结算单，其余照出。
  ADR-0012 的三道闸仍只管正式工资条。
- **没有月报就实时拉取**（杜总 2026-11-09 11:24；12:41 取消预览后仍成立）：
  删除前弹窗不读任何考勤数据；**确认删除时**才在钉钉离职之前调用
  `_sync_attendance_before_dismiss()` 实时拉取当月 + 上月（`sync_month` 按（员工, 月份）去重：
  有月报的月份跳过，没有的月份当场拉），拉完再用同一套 `_dismissal_plan()` 落库。
  ADR-0007 第四节同步。
- **预同步失败即整批不删**（D1）：钉钉里人还在、只是接口超时 / 限流 / token 失效 / 考勤组查询报错时，
  整体拦下并报错写明哪个月没拉到，管理员修好重试；**不给「仍要删除」的二次确认出口**。
- **4601「查无此人」是另一条支路**（C6）：预检阶段就被拦并由管理员人工核实，根本走不到预同步。
  确认后照常删人，只按本地已有月报出结算单；这条支路钉钉已查无此人，实时拉取也拉不到，
  缺月报的月份最终不出单，并写进删除后的结果消息（A3）。

## 四、出单范围与金额口径（2026-11-09 定稿，取代 C5 / D3 / D5 / E3 的旧绩效口径）

判据只有一个：**删除时，上一个自然月的正式工资条是否已经生成**
（即 `iac_salary_payslip` 中存在该员工上月、`generation_source != dismissal` 的记录）。
不引入 10 号、15 号或半个月日期常量（E2 的「10 号发薪、10 号之前工资条一定生成」只是业务惯例）。

| | 上月**已有**正式工资条 | 上月**没有**正式工资条 |
|---|---|---|
| 结算单张数 | **1 张**：离职当月 | **2 张**：上月 + 离职当月 |
| 管理员手填的那笔绩效扣款 | 写进**离职当月**结算单 | 写进**上月**结算单 |
| 离职当月绩效 | 按管理员填的扣款算 `max(绩效基准 − 扣款, 0)` | **全部扣除清零、不给他发**：实际绩效 0，`performance_deduction = 绩效基准` |
| 上月 | 不再出结算单（B7），避免重复发薪凭证 | 出上月结算单，绩效按管理员填的扣款算 |

- 弹窗**始终显示且始终可填**：扣款输入框不会只读、不会隐藏。管理员填的永远只有**一个数**，
  落到上表指定的那张结算单。
- 管理员填的扣款**不写 `iac_salary_performance_entry`**（B4），不进入全员绩效确认进度、
  不影响整月工资条生成。
- `performance_base` 一律保留薪资档案原值；绩效基准为 0 的员工实际绩效 0。
- 两张单都按拉取到的钉钉月报数值**原样计算**，不做额外折算，弹窗标注「数据截至离职日、可能不完整」（C4）。
- **月中离职的月报不覆盖整个自然月**（杜总 2026-11-09 11:24 明确）：月中离职 / 月中拉数时，
  钉钉返回的月报只覆盖到拉取当日（离职日），不是整月预排；金额按这份不完整的月报原样计算，
  **不按整月补齐、不按自然月天数折算**，弹窗显式写明这一点。原「上线后核对是否整月预排」
  的待核对项按此口径作废；上线仍需核对的是「拉取当日返回的字段确实截至当天」。
- 工资、全勤、缺卡扣款等其余字段沿用 ADR-0011 公式。
- **半个月与离职日判定不再参与绩效计算**：杜总 2026-11-09 定稿改用「上月工资条是否已生成」作唯一判据。
  半个月口径（当月自然天数 ÷ 2 向下取整，30 / 31 天月 15 号、2 月 14 号为界）与
  「离职日 = 当月最后一个有考勤结果的工作日」保留为**弹窗展示与提示语的业务背景**，不进代码分支。
  提示语「未满半个月无绩效，未满一个月扣除半月绩效！」固定显示，不参与计算。

## 五、锁定、通知与查看

- 删除确认前弹窗**可反复编辑**；确认删除才落库；**落库即锁定、只读**，任何人不能改（B7）。
- 结算单**不参与超管确认工资条、不发「工资已发放」钉钉通知**（人已离职，也发不到）。
- 工资条页：仅当所选月份存在 `dismissal` 记录时显示「查看离职结算单」按钮；
  **管理员与超管可见，普通员工不可见**（B9）。弹窗只展示该月**已生成**的离职结算单列表，
  字段与工资条同款，并标注「落库即锁定、只读、不参与超管确认」。
  2026-11-09 修正（杜总 11:24 / 12:41）：原写「并标注哪个月缺月报、哪个月已有正式工资条」
  整条废止。`iac_salary_payslip` 有 `(oa_user_id, month)` 唯一约束，**同一个月不可能同时有
  正式工资条与离职结算单**：本弹窗按月份列出的每张结算单，对应月份本来就没有正式工资条，
  标「已按正式工资条结算」是逻辑错误；标在正式工资条上又属多此一举。查看页只展示
  已生成的结算单，不补任何标注。

## 六、按定稿规则推导出的实施口径（如有偏差，实施前纠正）

1. 出单数量与绩效扣款落点只由「上月是否已有正式工资条」决定，不引入 10 号、15 号或半个月常量。
2. 定稿后「离职日」与半个月口径都**不进代码分支**（杜总「不用留」）：离职日能取到就在弹窗里
   作为展示信息，取不到显示「未知」；**不因判定不出而拦下该月结算单**。该月出不出单只看
   「该员工该月月报是否已存在」（第三节 E1）。原「判定不出不出单」是旧推导，随定稿作废。
3. 缺哪个月的月报，以实时拉取后的结果为准：仍无数据的月份不出结算单（C6 / E1），
   并写进删除后的结果消息（A3）；删除前不预判、不提示（12:41 取消预览）。
4. **2026-11-09 12:41 废止**：原写「已有正式工资条的那个月，按钮点开直接展示那张工资条
   并标注『已按正式工资条结算』（B7）」。同月不可能同时有两类凭证，见第五节；代码从未实现，
   随本节一并作废，不再保留为待办。
5. F1 / F2 两条旧推导随本定稿作废：一张单时扣款框仍可填，两张单时离职当月一律全扣光，
   不再有「满半个月按档案全额」「弹窗只读展示已结扣款」这两档。


## 七、被否掉的方案

- **独立建表 `iac_salary_dismissal_settlement`**：字段完全一样却要新表、新 CRUD、新接口和 prod 迁移，被否（C3）。
- **`status = 3` 当类型标志**：破坏确认状态语义，见第二节，被否。
  注意：2026-11-09 把结算单 `status` 置 1 是「确定状态」而非类型标志，与本条不冲突。
- **沿用「月中离职保持账号启用到月末、工资条生成后再走离职」**：与实际删除时点冲突，废止（ADR-0011 修订 2）。
- **结算单照搬 3 日闸 / 月份闸 / 全月同步闸**：绝大多数离职会出不了单，被否（E1）。
- **离职当月等月末补齐考勤再算**：钉钉离职后拉不到，被否（C4）。
- **两张单的第二张绩效也由管理员手填**：与「一个扣款」冲突，被否（C5 / D5）。
- **把提示语「未满一个月扣除半月绩效」实现成自动计算规则**：杜总 2026-11-09 纠正，提示只是提示，被否。
- **把提示语 / 缺月报提示放到薪资绩效 Tab 的「登记绩效扣款」弹窗**：杜总 2026-11-09 11:24
  纠正，那是生成工资条前的全员绩效登记，不是删除员工时登记离职扣款的地方，被否
  （取代 11:11 的临时理解）。
- **删除前做结算预览（出单月份 / 预估金额 / 缺月报提示）**：杜总 2026-11-09 12:41 拍板取消。
  预览依据是旧月报，与「确认删除时实时拉取」冲突，管理员取消删除时预览数据毫无意义，被否。
- **「缺月报显式提示」**：A2 取消，理由见第三节，被否。
- **在「查看离职结算单」弹窗标「已按正式工资条结算」**：逻辑错误（第五节），被否。
- **按半个月 / 离职日自动算离职当月绩效**：定稿改用「上月工资条是否已生成」作唯一判据，被否。
- **上月已有正式工资条时把扣款输入框设成只读**：定稿要求弹窗始终显示、输入框始终可填，被否。
- **预同步失败只记日志继续删**：会永久丢考勤，被否（D1）。
- **停用时也生成结算单**：停用可逆、不是离职，被否（A9）。

## 八、实施验证清单（代码阶段）

- 结算单落库后 `month_generated()` 仍为 false，正式工资条能正常生成、当月绩效仍可改。
- `confirm_payslip()` 对 `dismissal` 行拒绝，不发钉钉通知。
- 两张单：上月结算单按管理员扣款算、离职当月实际绩效 0 且 `performance_deduction = 绩效基准`。
- 一张单：离职当月结算单按管理员扣款算，上月不生成结算单、弹窗仍可填。
- 批量删除多人（含无绩效奖金员工）、4601 支路、缺月报月份。
- 删除弹窗不出现任何金额 / 出单预览；删除成功后的 `msg` 带生成张数与未出单月份（A1 / A3）。
- 一月跨年默认月份与服务端 3 日闸（见 ADR-0017）。

## 九、实施口径（2026-11-09 代码阶段，按定稿推导；如有偏差请纠正）

## 十、2026-11-11 补记：与「月中入职」划界

第四节「月中离职的月报不覆盖整个自然月……**不按整月补齐、不按自然月天数折算**」保持，
本次 ADR-0011 第十一节的「应出勤按全组统一」**不适用于离职结算单**：
`_dismissal_plan()` 调用 `_calculate()` 时不传 `required_override`，仍按个人月报的 R 原样计算。

两者不是同一类问题，不得互相类推：

| | 月中入职 | 月中离职 |
|---|---|---|
| 钉钉月报 | 只覆盖入职后被记到的日期，分母 R 被截短 | 只覆盖到拉取当日（离职日），本就是不完整月报 |
| 后果 | `A/R = 1` → **多发**整月工资 | 按不完整月报原样算，金额天然偏少 |
| 处置 | R 抬平到全组标准（23），A 按实际到岗人工认定 | **不补齐、不折算**，原样出单 |

回归测试：`backend/tests/module_internal/test_new_hire_proration.py` 中
`test_dismissal_plan_keeps_personal_required` 守住这条边界。
