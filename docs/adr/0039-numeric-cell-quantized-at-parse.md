# 数值格子在「读文件那一步」就量化到它落库列的精度，方向写死

2026-10-29 用户口径：「AF5，包括其他的，**导入和更新的算法要一致**。不要因为这个引起错误数据。」

AF5 把四列快麦源值的钱统一到一把尺，但那一轮是按「哪一列出过问题」列举的，不是一条规矩。把它当成规矩扫一遍全部业务代码后，还剩四格没进这套口径，其中**重量这一格在真实数据上已经在改钱**：

- 导入侧（`order/importers/excel_source.py`）的 `重量kg(SKU)` 走 `_to_decimal_or_none`，**读到几位就带几位往下走**，整到 3 位这件事是**数据库代做的**（列是 `Numeric(10,3)`，MySQL 的 DECIMAL 舍入是四舍五入 / half away from zero，`0.0025 → 0.003`）。
- 更新侧（`order/service.py::_diff_detail`）的重量分支自己量化，用的是 `.quantize(Decimal("0.001"))`——**没写方向，Python 默认就是凑偶**（ROUND_HALF_EVEN，`0.0025 → 0.002`），然后把 0.002 写回库里那个 0.003。
- 于是**同一份文件先导入、再用它跑一次更新，18 个重量格子的数字会变**。而重量正是运费摊分的权重（`logistics/service.py` 的 `_WaybillGroup.weight_keys = weight_kg × ship_qty`），权重差 0.001kg，这一票运费在几条子订单之间的归属就跟着挪——总额还对，行级与店铺级的归属已经错了。这正是用户说的「不要因为这个引起错误数据」。

实测依据（只读扫桌面 `9月数据.xlsx`，5568 个数值）：`重量kg(SKU)` 列有 **132** 个格子带 4 位小数，其中 **18** 个恰好压在进/舍的分界上，凑偶与四舍五入给出不同值（三种形态：`0.0025`、`0.0165`、`0.3105`）。

## 决定

**一条规矩，覆盖所有「文件格子 → 落库列」的数值**：

1. **在解析那一步就量化到它落库那一列的精度**，不等数据库代劳。落库列就是精度的唯一来源——金额列 2 位、重量列 3 位、成本价列 4 位。
2. **舍入方向一律显式写 `ROUND_HALF_UP`**（四舍五入、ties away from zero）。选它而不是选 Python 默认的凑偶，理由与 Z1/AF5 同源：MySQL DECIMAL 一直在做的就是 half away from zero，显式写 HALF_UP 等于**把数据库已经在做的事说到明面上**，因此存量数字一个都不需要订正、也不需要重跑导入。
3. **比较、求和、告警、写库只用这个量化后的值**。拿原始精度值去跟库里的量化值比，就是「同一份文件重跑更新每轮都判它有变化」的来源（AF5 已经在四列钱上治过一次，这次是重量与成本价）。
4. **导入与更新两条路径复用同一个量化函数**，不允许一侧交给数据库、另一侧自己 quantize。

按这条规矩要动的格子：`重量kg(SKU)`（3 位）、`成本价(SKU)`（4 位）、账单的`账单重量`（3 位）与`账单其它费用`（2 位，含非账单行/合计行那些格子，因为它是**对账基准**，不同尺就会报出一条假的「合计行与逐行求和不一致」）、快麦 API 数据源的四列钱（那条路现在必抛、未接线，不补就是留一颗延迟引爆的雷）。另外代码里还有三处 `.quantize()` 没写方向（运费摊分的单份份额、批次备注的展示格式化、主订单运费求和），全部补上显式方向——术语表「见位进分」那条的 `_Avoid_` 已经写着「凑偶任何路径都不用」，写死方向是让这句文档不再说谎，而不是新增规矩。

**本条只管「量化在哪一步做、方向写不写」，不管「用哪把尺」**：算出来的金额照旧见位进分、快麦源值照旧四舍五入到分（AF5），这两把尺的分野不被本条改动。

## 代价

- **摊分的单份份额方向从凑偶改成四舍五入，会改变「同一条子订单拿到哪一分」**，但**不改变总额**：`_apportion` 的余数照旧补给权重最大的那条，Σ份额 与整票金额仍然逐字相等（ADR-0034 的不变式不受影响）。`ecommerce_courier_bill` 现在 0 行、账单批次全部 `unconfirmed`、子订单 `freight_cost` 尚未回写过 → **无存量可动**。
- **批次备注里报的求和变成「库里那些行的值」之和**，与文件原值的肉眼求和可能差在 0.001kg 这个量级。这是要的：备注是让人拿去跟界面/库里逐行核的，报一个库里查不到的数只会让人怀疑系统算错了。代价是**真实的合计行差异会更早暴露**（本来被两侧不同的舍入掩盖掉的分位差会显出来），那是多报一条核对提示，不是错数。
- **成本价告警的口径变严**：`成本价(SKU)` 与主表比较改成两侧都按 4 位比。原先「文件给 3.11094、主表 3.1109」会报一条不一致的假告警，现在不报了；反过来「文件 3.111 与主表 3.1109」以前会因为两侧精度不同而漏报的情况，现在照报。
- **尺子收成一份，落在 `module_ecommerce/common/numbers.py`（本轮新增文件）**。原先 `_round_cent` 在 `order/service.py` 与 `order/importers/excel_source.py` 各写了一遍，注释还理直气壮地解释「导入侧不能 import 服务层，会成环」——成环是真的，但把尺子放在服务层才是问题：`common/` 的准入声明（ADR-0035）说的就是「电商多个子域共用、且不是外部系统对接的代码」，而「一个 Excel 格子落到某一列」订单与账单两个子域都在做。**拷贝本身就是下一次走岔的入口**，一条要求「导入与更新复用同一个量化函数」的规矩，代码里却留着四份长得一样的函数，那是文档与代码互相指认。所以这一轮把精度常量（2 位钱 / 3 位重量 / 4 位成本价）与 `ROUND_HALF_UP` 三个入口一起放进 `common/numbers.py`，五个调用方（`excel_source`、`kuaimai_api_source`、`order/service`、`generic_parser`、`logistics/service`）全部改成引用它。
  **见位进分 `_ceil_cent` 仍留在 `order/service.py`**：只有那一条路径用它，挪进 `common/` 是把「谁也用不到」的东西塞进公共层。**R 轮的「Excel 脏值原语合并」挂账没有因此清掉**，只是范围缩小了：剩下的（`_EMPTY_TOKENS` 空值词表、`_to_str_or_none`/`_to_int`、表头扫描两侧的取值口径）动的是**报错与空值语义**，回归面仍是全部三条导入路径，本轮不借这股本该只动方向的改完。**〔那半桩挂账 2026-11-07 已定为不做，见本文末尾「脏值词表不合并」那条。〕**

## 验收钉子

新增一条**幂等不变式**，是本轮唯一的「真做过」证明：**同一份文件先导入、紧接着用同一份跑更新，必须报「无变化」，且每一个数值字段落库的数字与「只导入」时逐字相等**。这条一旦有任意一格用不同的尺，更新就会写出一个不同的数——AF5 那轮只能靠「先手工造一个旧值」才能验到更新侧的尺，就是因为这个不变式当时还没立起来。

## 实测依据（2026-10-29，回滚式脚本 `verify_ag_round.py`）

AG 组 98/98 全绿；六套旧回归一并重跑无退化（AF 74、AC 55、AB 33、确认路径 12、AE 12、AE 检索机制 10）；`ruff check app/plugin/module_ecommerce --no-fix` 干净。三条量出来的关键事实：

1. **幂等不变式成立**：一份带 4 位重量（`0.0025`/`0.0165`/`0.3105`）、5 位成本价（`3.11094`）、厘位金额（`10.004`）的文件，导入后连跑三遍更新，每遍都是 `成功更新 0 单…另有 1 单无变化`，15 个数值列 + 主订单 6 个聚合数逐字未变，更新备注一条没写。分销行同样成立（`0.017`/`3.1109`/`7.72`）。
2. **「存量不需要订正」是量出来的，不是形容词**：真实库 `ecommerce_order_detail`/`ecommerce_sku_cost`/`ecommerce_courier_bill` 共 **27532 个数值**逐个数与新尺子比对，**0 个会被改写**；同时实测 MySQL `ROUND()` 的方向就是四舍五入远离零（`1.025→1.03`、`-1.025→-1.03`、`0.0025→0.003`、`0.0045→0.005`、`3.11085→3.1109`），且每一格都与 Python 默认的凑偶结果不同。库内 22 个 DECIMAL 列全部在「尺子清单」里、scale 与代码那三把精度逐列相等（以后新增数值列没配尺，这条探针直接失败）。
3. **告警没有变哑**：真的不一致照样报（文件 `3.11095` vs 主表 `3.1109` → 报 `成本价(SKU) 3.1110 与系统成本价 3.1109 不一致`），且报出来的文件价是量过的 `3.1110`，不再是一个库里根本查不到的 5 位数。

**验证时当场抓出并修掉的一处本轮新引入的洞**（写在这里是因为它正是这条规矩要消灭的那类错）：账单「其它费用」的负数闸原先写在 `or Decimal("0.00")` 兜底**之后**，`-0.001` 量化成 `-0.00` 是个假值，被兜底换成正的 `0.00` 静默落库——把一格快递给的脏负数收成 0，还不告诉任何人。把闸挪到兜底之前（判 `is_signed()`，`AG4-05` 锁住）。这一类「先舍再判」的坑是量化进了代码才出现的，说明这轮改动本身也需要那条不变式兜着。

**旧断言的就地修订**（不重编号）：`AF5-09` 原断言「重量 `0.5004` 原样透传」是 AF 轮那把只管钱的尺的口径，被本轮的总规矩推翻，保留编号、改成断言 `0.500` 并写明是 AG 轮修订。

## 修订（2026-11-02，AN13）：成本价的刻度从 4 位改成 2 位

业务方原话「成本价 2位，不是4位，这个要改文档，选甲」。**这条 ADR 的骨架一件都不动**——数值仍在读那一格时定形、导入与更新仍复用同一个函数、算出来的金额仍走见位进分、快麦源值仍四舍五入到分。改的只是「成本价这一列拿什么尺子量」。

但**改的不只是刻度那一个数字**，业务方随后把「怎么量」也改了（AN16 原话「不用舍、进位，只需要报错」，AN25 补答「快麦的订单如果 2 位以上不拦，但是主表只能最多 2 位」）：**例外只立在「我们录的价」那一侧**——商品成本主表的新增与编辑，小数第 3 位非零就是报错，不替你舍平再收下（这张表**没有** Excel 导入入口，见设计文档 §26.13 第 4 条）；快麦订单「成本价(SKU)」那一格**照旧按列精度量化到 4 位存原值**，它是别人报给我们的凭据，不进利润。比对时**原值直接比**（AN28=甲）：快麦给 `10.504`、主表 `10.50` 要报成一条不一致，因为这条告警的作用就是提示人去把快麦那一格改对——先量化再比等于把要提示的那一半抹掉。为什么这条例外不破坏本 ADR 要治的病：本 ADR 反对的是「两侧不同尺」，而拒收闸同样立在**值进入系统的那一步**、主表的新增与编辑两条路径共用同一个 `over_cent`，所以幂等不变式照样成立——只是"过了闸的值"必然是整到 2 位的，落库时不再发生舍入。

**闸落在服务层而不是字段约束**：Pydantic 的 `decimal_places=2`（§25 面单费用的就是它）报出来是那句英文 "Decimal input should have at most 2 decimal places"，说不出「收到的是多少、该改成什么」；服务层用 `common/numbers.py::over_cent` 判、把原值报回给录入的人。面单费没有存量超位问题，所以那一格不动。

**这条例外给存量带来的副作用（2026-11-02 实施时确认）**：库里已有的 64 行主表成本价带 3~4 位小数（AN15 决定**不刷**、只出清单），闸立在保存那一步，所以这些行**改任何一格都会被打回**，必须先把成本价写成 2 位才保存得下去。同理，商品成本弹窗的成本价输入框**不加 `precision=2`**（面单费那格有）：`ElInputNumber` 的 precision 会在挂载时就把 `3.1109` 显示成 `3.11`，打开一次再保存等于替业务方把账改了——那正是 AN13 要避免的事。超位那一格在界面改不掉，直到 §26.13 那批存量订正做完。

**存量按业务方指示不动**（AN15「存量不管，你帮我标记一下，等系统开发好，我再统一处理」；AN24「现在只改仓库，数据库内、还有 excel 上面的，都到时候统一做，你后面提醒我」）。因此 `Numeric(12,4)` 这三个列**此刻还不改**：改列 = MySQL 在 `ALTER` 里自己把那 64 行（主表）舍掉、连带重写 74 行历史快照，与「存量不管」正面冲突。**「统一做」那一批的清单挂在设计文档 §26.13，动它之前要点名提醒业务方**。实测数字、订正清单与各条答复（AN17/AN19/AN20/AN24～AN28）全部记在设计文档 §26.9～§26.12，本轮只写录入侧那道闸与导入侧的必填闸。

**2026-11-06 「统一做」真正执行时，上面那句「三个列」缩成一个列**：业务方复核当日 SQL 的话是「快麦导出订单在数据库里的值……只做拦截，不对数据库中原本数据进行处理……**要数据订正的是商品成本表**」。所以本 ADR 那条例外的最终形状是——**主表 `ecommerce_sku_cost.cost_price` 收 2 位 + 录入侧拒收第 3 位；订单侧 `cost_price`/`excel_cost_price` 连列带存量都不动**，「按列精度量化到 4 位存原值」那一句原样有效，`COST_QUANT` 继续有调用方。历史快照与刷过的主表之间会留下 **12.62 元**的差（22 行发货成本），它不进本轮订正，等那份 9 月文件下一次走订单更新时按新主表自己回填——这是「拦截新的、不改旧的」这条口径的明码代价，记在这里免得日后被当成 bug 重修。

**2026-11-06 这一列已经收掉了（同日执行）**：`ecommerce_sku_cost.cost_price` 现在是 `Numeric(12, 2)`，模型列与 dev 库同步到位；订单侧那两列照旧 `Numeric(12, 4)`。**生产不需要迁移文件**——本框架的空库首次启动走 `create_tables()`（`app/scripts/initialize.py:68-80`）按 ORM metadata 直接建表、再把迁移历史 `stamp` 成 head，整条 revision 链在生产上一行都不跑；`app/alembic/versions/` 进仓库的只有 `__init__.py`（本地那些文件全是 dev 自动生成的）。所以生产首建出来的这一列天然就是模型里那 2 位。dev 库这边因为表已存在、`create_all` 不改列，实际是**改完 `order/model.py` 后由 dev 自动迁移（`initialize.py:88-94`）生成并当场应用了 `23b901e40b7e`** 这一份 revision 收掉的；随后独立跑的执行脚本又幂等地发了一次同样的 `ALTER TABLE ... MODIFY`，并核对「改前残留 0 行」与「改前改后 1454 行逐字相等」——这一条 DDL 不动任何数字。**配套同轮改掉的三处**（漏一处 AG 回归当场红）：`verify_ag_round.py` 的 `expected_scale` 那一格 4→2、`AG6-06` 不动点扫描里同一格 `COST_QUANT`→`MONEY_QUANT`、以及 `common/numbers.py` 与本 ADR 里那句「成本价列 `Numeric(12, 4)`」限定成只对订单侧成立。**跑出来才现身的还有五处**：`AG2-02`（原先断言「文件 3.11094 对主表 3.1109 不报」——主表已是 2 位，这一格现在是**真不一致、必须报**，AN28 原值直接比）、`AG2-16`（改指「3.11095 报、尾零 3.110 不报」，同一条尺子的两面）、以及 `verify_an_round.py` 的 `AN2-10`/`AN2-12`/`AN5-9b`（绕过服务层硬塞的 4 位**存不进主表了**，MySQL 在写入时收成 2 位；快麦那侧仍留 `3.1109`）。前两组是「预判对了」，后五处是「预判漏了、靠回归兜住」——这两件事分开记，免得日后以为改列只需要同步三处。

**空格子也过同一把尺（2026-11-03 AN31）**：`excel_source.py::_to_decimal` 里「这一格空着」那一支原先短路返回**没量过的** `Decimal("0")`——数值没错，刻度不对，而本文第 1 条写的是**每一格**都在读那一格时定形。现在它返回 `round_cent(Decimal("0"))`，读出来是 `0.00`。落库还是同一个 0，**没有任何数字变化**；改的是「不许留一支不量化的路径」这件事本身——验证脚本原先被迫断言一个假刻度（`0` 而不是 `0.00`），就是这类例外在文档里的影子。

**脏值词表不合并（2026-11-07 业务方定，这笔 R 轮挂账就此销掉）**：业务方当场核对真实导出——快麦订单的重量列只有 `0` 和数值、成本列同样、实发实退是含 `0` 的整数；快递账单的重量与三项费用也没有特殊符号；只有出库单的「店铺全称」那一格写 `-`。三份词表里 `--` `/` `无` `暂无` 于是被证明是我凭空加的防御，一次都没出现过，「合一份免得下次走岔」的收益塌了一半，而代价（`common/` 新增文件 + 三条导入路径重跑回归）没变。**结论是不做，同时也不许反过来收窄**：多认几种非数值写法不会把有值判成空，零风险零收益；收窄则把「当空」改成「整份报错」，那是行为变化，不该夹在一次销账里。**这两份词表永远不能取并集**，理由与 ADR-0023 同源：店铺那份必须认 `0`（出库单拿 `0` 当店铺编码），数值那两份绝不能认 `0`——件数 `0`、成本 `0` 是有意的值。随之量清的现状（只读探针，SELECT + 回滚）：`0` 存成 `0` 的有 **1433 行**，所以「0 被当成空」这个担忧在库里不存在；`weight_kg IS NULL` 的 **586 行**里 **523 行**是「未走 ERP 发货 + 实发 0 件 + 成本也 NULL」，即整行本来就没数字（未发货/关闭单），**与脏值无关**；剩下 **63 行 / 55 张主订单**（全在 `order-2026-09`）是「ERP 发货、有件数、没重量」——这是快麦那一格要不要补的数据问题，不是代码问题。销账记录在设计文档 §11「本期挂账」最后一条。
