# 运费回写进子订单，取消独立匹配表；判重只认原件行

运费计算原先是「账单行 → 匹配表 → 按归属月聚合」三段式：`ecommerce_freight_match` 既存匹配关系，又存面单费/实际运费快照，还兼异常标注。实际用起来发现这张表把三件不同的事绑在一起，每一件都更适合放在别处，于是整张表删除，运费改为**直接回写到子订单上的一条可空金额列**，账单行自己承载状态与异常原因。

**为什么回写而不是留匹配表**：一票运单对应的子订单是确定的少数几条，摊分结果就是这些子订单自身的属性（这一票花了多少运费），不是需要独立生命周期的第三类业务对象。留中间表的代价是每次算利润都要跨表聚合、每次重算都要先清后写，而收益只有「保留匹配过程的历史」——这份历史账单行本身就有。删表唯一真正丢失的是按票快照的面单费，因此在账单行上新增面单费快照列补回。

**两个时间维度必须分开**：**出账月**是账单文件属于哪个月（快递公司的账期，人工填写、行级账单日期必须落在其中），**发货月**是子订单实际发货所属的月份（运费与利润的归属依据，ADR-0025）。此前两者混用，才导致「按归属月查找、找不到回溯上月」这套逻辑。改成**全局按运单号在 ERP 发货子订单中查找**，命中几条摊几条、跨几张主订单都挂上，回溯逻辑随删表一并废弃。理由是运单号本身全局唯一，出账月只决定这张账单什么时候导、不参与「这笔运费属于哪个月」的判断；靠月份去限制查找范围，等于用一个不相关的维度去猜一个已经能确定的键。

**判重只跟「原件行」比**。一个运单号的运费只应计一次，所以只有能挂上 ERP 发货子订单、且状态为「已匹配 / 重量省份异常 / 已恢复」的账单行才算原件行——重量省份异常只是提示核对、不动钱，它照样是原件行；后来的同运单号行才判为重复。逻辑删除的行和「虚假异常」行都不构成历史。这条规则把优先级定为**虚假 > 重复 > 重量省份**：两条都挂不上订单的虚假账单叠在一起时，判成重复反而掩盖了真正的问题（两条都是虚假），所以它们各自标虚假、不互相判重。同批次内同一运单号出现多行时按行序第一条当原件——前提是一个批次里一个运单号只该出现一次。

**只有原件行参与回写**，重复行与虚假行的一分钱都不进成本。原先匹配表里重复/虚假记录仍带全额运费，靠下游聚合时小心排除来保证正确，这是一个随时可能被人漏掉的坑。

**回写只发生在账单批次确认那一刻，且是覆盖式**（重算直接盖、不累加），同时刷新主订单的运费求和。因此「重新确认」是安全的：即使日后订正数据库把批次退回未确认再重新确认，出来的仍是同一份数字。这条幂等不变式是选择覆盖而非累加的唯一原因——累加在重算下必然翻倍。覆盖式还带来一个必须跨批次求和的推论：同一个运单号允许有第二条原件行（把重复行人工改对后置「已恢复」就是这个动作），若确认第二个批次时只对本批次的行求和，就会把先确认批次写进去的运费盖掉、钱静默消失；所以摊分的整票金额取该运单号**全部**原件行之和，其中只算已确认批次与正在确认的这个批次——未确认批次的行还是原始数据，没资格进成本。回写不受订单批次的确认状态限制（账单可能晚于订单确认），但触及已确认订单批次时会在该批次详情留一行「改动了 order-2026-09，需重算利润」，自动通知与自动重算本期只留空方法。

**摊分完全按重量**（Σ 重量×实发件数），因为一票里各件商品确实轻重不同；整票重量全空或全 0 时退化为按实发件数摊，件数也全 0 则标异常、挡住确认。**只有 `ERP发货` 的子订单参与**——`其他ERP发货` 是平台侧自行填写单号发货，运费与本公司账无关，`未发货` 更不成立。缺账单因此不需要扫描任务，退化为一条纯查询：`ERP发货` + 运单号非空 + 子订单运费为 NULL。人工把 NULL 改成 0 即视为处理完毕，下月真账单来了覆盖式回写会让它自然出列。

**子订单运费列沿用 ADR-0023 的三态语义**：NULL=还没定、0=人工有意按 0 计、大于 0=账单实额。用 NULL 而非 0 表示「还没定」，是为了让缺账单查询有得可查——若缺失也写 0，「确认没有运费」和「账单还没来」在数据上无法区分。

**账单行状态收成单列五值**（已匹配 / 虚假异常 / 重复异常 / 重量省份异常 / 已恢复），并删掉原先的 `match_status` 列。两列表达的是同一件事的两半——匹配到哪一步了、有没有问题——分开就会出现在一列改了另一列没改的矛盾行；「已恢复」是人工把异常行改对之后的终态，它必须与「已匹配」区分开，因为前者是被人判过的证据。删除动作只允许作用于未确认批次里的虚假行与重复行，且走框架的软删除，重量省份异常不允许删（它是提示核对而非确认可删的垃圾数据）。

> **「已恢复」可以再改回虚假/重复**（2026-10-27 补，AB1=甲，设计文档 §16.2）。改对是人工判断，判错了原本只能整批作废重导——为一条行重导一份账单代价太大。撤销时**由人指认**改回虚假还是重复（系统不存改对前的原状态，为此加列不值），并且**把这一行的 `actual_freight` 归零**：已恢复是原件行、它的钱进摊分，改回非原件行后钱必须退回去，否则第一条推论里的「全部原件行之和」会拖进一条不该算的钱。删除 / 改对 / 改回三个动作共用同一道闸：行状态匹配 **且** 所属批次未确认。

> 行级软删与**批次作废**是两件事，别混：作废针对整条未确认批次，连行带批次**物理删除**，为的是腾出被占住的 `bill-{类型}-{月份}` 唯一批次号（软删挡不住唯一索引）。见 ADR-0033。

> **摊分单份份额的舍入方向写死四舍五入（2026-10-29 决议 AG4，见 ADR-0039 与设计文档 §21.3）。** 上面那句「摊分完全按重量」没管权重那一格本身怎么来的，也没管单份份额怎么舍。两处现在都补了明确方向：份额逐条 `.quantize(0.01, ROUND_HALF_UP)`（原先是默认凑偶），作为权重的 `重量kg(SKU)` 在**读文件那一步**就整到 3 位（原先导入交给数据库舍、更新自己凑偶，同一份文件跑一次更新就把 0.003 改写成 0.002）。**这两处都不改变本文的不变式**：余数照旧补给权重最大的那条，Σ份额 与整票金额逐字相等，覆盖式重算的幂等性不受影响——方向只决定「同一条子订单拿到哪一分」，不决定「这一票总共多少钱」。真正会挪钱的是权重被两侧不同尺改写，那正是 ADR-0039 要治的。

> **虚假行「改对」在本文原口径下根本走不通，AI 轮用「认领订单」把它接通（2026-10-29 决议，设计文档 §22）。** 上面那句「人工把异常行改对后置『已恢复』、它的钱随批次确认参与摊分」漏了一件事：虚假行的定义就是**运单号查不到任何 ERP发货且非分销的子订单**，而确认时的寻址线只有运单号这一条——`restore_bill_rows` 翻完状态、存好金额，`_write_freight` 仍然在这一票上抛异常、**整批确认失败**。所以「改对」这条路以前只有重复行能用，虚假行唯一的出路是删。本轮补的动作叫**认领订单**：人工指认这一票属于哪张主订单，把**账单上的运单号写进那张单里勾选定的子订单行**（可多选；一张单里勾多条就是一票分包发），运单号这条寻址线自己就通了，钱照旧只在批次确认那一刻进子订单。**摊分规则一个字没改**：`_apportion`、`_collect_waybill_groups`、`_write_freight` 原样，本文那条「覆盖式 ＋ 跨批次取全集 ＋ Σ份额＝整票金额 ＋ 幂等」的不变式不受影响，也**不新增认领池**——被否掉的认领池方案要求同一条账单行同时挂在运单号和人工单号两条线上，随之冒出双算、两池撞同一条行时覆盖式静默吞钱、为撤销再加一列这三件事；业务方给的口径是「订单确认之前新订单被发现，那就按一般逻辑来，同一个运单号运费按多订单分摊」，而这恰好就是现有行为。撤销凭据不占新列：被改的那条子订单行在自己的**「更新备注」**里留一段带批次/行号的订正标记与原值，重新订正时**只退回带标记的行**，订单侧后来自己导入出同一个运单号的行不会被擦掉。订正也不会被后续订单更新冲掉——运单号不在更新比对的 9 个字段里。

> **上面那块「『已恢复』可以再改回虚假/重复」在 2026-10-29 AI 轮整条作废；AJ 轮把 AI 轮唯一保留下来的补救入口「重新订正」也一并删掉**（业务方口径：确认过的就是确认过的，不能改也不能退回。清单见设计文档 §22.5、§23）。于是「删除 / 改对 / 改回三个动作共用同一道闸」现在只剩**删除与改对**两个动作，那道闸本身（行状态匹配 **且** 所属批次未确认）不变；删除仍只给虚假/重复行，「已恢复」因此不是单行道而是**终点**：不能改回、不能删、也不能换勾选的子订单行，界面上这条行的「改对/删除」**置灰点不动**（按钮还在，不是点了才报错——2026-10-30 浏览器验证收口的界面口径）。要撤销这一票的成本判定，只能由能改数据库的人同时改订单表的运单号和账单行的状态。
>
> AI 轮那句「**留痕即凭据**：重新订正时只退回带标记的行」同时作废：订正标记照旧写进子订单行的「更新备注」（带批次、行号和原值），但**只写不读**，没有任何代码再解析这段文字。AI 轮自己认下来的那条技术债——「文案一改或有人在库里手工编辑过备注，退回就会失准」——随撤销功能一起消失，代价换成上一条那句实话：写错了没有界面补救。

> **上面那句「缺账单退化为一条纯查询」的入口位置在 2026-10-30 AK 轮改过：查询挂在主订单列表上，不是挂在展开行里**（设计文档 §24）。这条纯查询存在的理由是「漏导一整家快递不做倒推报警，靠缺账单列表变大自己暴露」——要能看见列表变大，筛的就必须是**主订单**：命中 = 该主订单下 `EXISTS` 至少一条缺账单子订单。原先实现把勾选框做在订单展开区顶部、参数只传给子订单列表接口，等于要求使用者先知道哪张单缺、点开、再勾，正好问不到它唯一该回答的问题。判据四个条件一个字没动（`ERP发货` + 运单号非空 + 子订单运费 NULL + 非分销，最后那条随 ADR-0036），改的只有它挂在哪张表上；判据今后只住在 `OrderCRUD._build_conditions` 一处，子订单接口那个同名参数一并删除，不留第二条能各自漂移的口径。**本文其余部分不受影响**：缺账单仍然是纯查询状态，不建表、不加标记列、不做扫描任务。

> **「未发货」认的是那个值的意思，不是那一格的字符串（2026-11-03 AN 轮实测，设计文档 §26.12 AN30）。** 本文与 ADR-0039 那条「未发货行整行不入库」一直按**精确字符串**比对「是否ERP发货」，而业务方给的 9月导出里有 **43 行写的是 `[未发货]`**（外面套一对半角方括号）。结果这 43 行既没被 AN27 新立的三值白名单拦下报错、也没被「未发货不入库」丢掉，而是带着 `is_erp_shipped=False` **落了库**，并通过 `_keep_shipped_totals` 参与了所属主订单的买家已付/退款/运费求和——本文那条「未发货不进收入、不进成本、也不进运费」在真实文件上是破的。修法只动**识别**这一层：比对前剥掉外面那对括号（`excel_source.py::_normalize_shipped_flag`），认出来的「未发货」照本文不入库，认不出的写法照 AN27 整份报错、且报错里读的还是文件原样。**本文的判定与摊分规则一个字没改**；库里那 43 行是既成事实，删行与重算归入设计文档 §26.13 的「统一做」那一批，等业务方点头。

> **认领这条线上，一个运单号只许有一张原件行（2026-11-03 实施，设计文档 §26.5 乙）。** 上面那句「同一个运单号允许有第二条原件行」说的是**重复行人工改对**那个场景（快递真收了两次），但**认领**一直不受它约束：同号的两张行都因为查不到子订单而各自标虚假（本文「虚假 > 重复」那条优先级决定的），第一张认领成功之后它成了原件行，第二张照样能认领成功——因为 `old_waybills` 那道闸算的是「勾选行**旧**单号被别人占着」，而第一次认领刚把勾选行的单号写成本票的号，正好被那个 `!=` 排除掉。于是两张原件行进同一摊分组、`total_amount` 是两份钱，**一票 1.90 摊成 3.80**，直接进成本进利润。修法只加一道闸、只在认领这一条线：认领前先看本行 `waybill_no` 上有没有挂着**别的**原件行，有就整笔拒绝并点名那张行的 id 与批次。判定优先级不动、摊分不动、「允许跨批次第二张原件行」那条推论不动，所以「重复行不填单号直接改对」仍造得出同号两张原件行——那是有意留着的，本轮没把它一起关掉（业务方定的就是「只在认领那一步加一道闸」）。界面代价照旧写在明处：同号那第二张在界面上仍叫「虚假」，不会自动变重复，要人工删。

> **人工认领有月份窗口，自动匹配没有——这两条线本来就不该同宽（2026-11-05 实施，设计文档 §26.6）。** 本文的自动匹配从头到尾**不看月份**：`_load_shipped_details_by_waybill` 全局按运单号取「ERP发货 且非分销」的子订单，那条子订单躺在 `order-2026-08` 还是更早的批次都照样匹配上。认领这条路原先要求目标订单在 `order-出账月` 同一批（AI 轮的四道闸之一），出账节奏一滞后就走不通——而**账单比订单更滞后是常态**：9 月底的货进 10 月的账单，10 月的账单 11 月才拿到。本轮把它放开到**出账月当月或上一个月**，再早的历史月仍拒。
>
> 为什么一边无限制、一边只放一档：自动匹配的证据是**订单行里本来就写着这个运单号**（快麦导出时 ERP 已回填），撞上就是撞上；认领是**拿人手打的订单号去改订单数据**，写下去还是终点（AJ 轮：不能改回、不能换行），所以要一条「这一票大致该是哪个月」的护栏，且护栏必须落在**出账月**这个账单自带的值上，不能落在"今天几号"——操作员哪天点导入不该改变闸门开合。
>
> **摊分与回写规则一个字没改**：认领当场一分钱不进订单，运费仍在确认账单批次那一刻按「本批次 + 其它已确认批次」的同号原件行全集现算现写、覆盖式落库（本文「覆盖式」那块）。改的只有「这行运单号写得进去吗」这一层。界面代价照旧写明：跨到上月那一档之后，一票运费有可能被摊进上个月已经确认过的订单——那正是 ADR-0033 末尾那条例外通道，以及「改动了 `order-YYYY-MM`，需重算利润」那行提示存在的原因。
