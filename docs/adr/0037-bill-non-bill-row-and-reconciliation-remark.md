# 账单「非账单行」以账单日期能否解析为判定；对账结果只写批次备注，不设门禁

2026-10-27 用户界面点检时发现：**带合计行的账单文件整份导不进来**，报 `第24行: 运单号不能为空`。根因在 `logistics/parsers/generic_parser.py:107`——运单号那道闸**排在日期校验之前**，而快递合计行恰好是运单号为空的那一行。订单侧早就处理过同一形态（`序号=汇总`，§5.1 与 AB6），账单侧压根没做。

## 判据只看一件事：那一行的账单日期是不是一个合法日期

**「账单日期」格为空、或者那个值解析不出合法日期 → 这一行是「非账单行」**，不入库、不算钱、不报错，但要**逐行**记进批次备注（行号 + 那一行的重量与费用）。

- **不认「汇总 / 合计 / 总计」字样**：字样是各家快递的自由文本，认不完；而合计行天然没有日期，日期这一条判据把它和所有其它"不是一票货的行"一起覆盖了，不需要为它单列规则。
- **不看运单号空不空**：运单号为空但**日期合法**的行，仍然照原样报 `第N行: 运单号不能为空` 并整份不落库——那才是真的数据缺陷。
- 因此**校验顺序必须改**：日期判定挪到运单号那道闸之前。这条顺序本身是本轮 bug 的成因，写在这里是为了下次不再被"先查必填列"的直觉带回去。

**接受的代价（本轮最危险的一条）**：账单日期是解析规则里映射的一列。**一旦那一列被映射错、或快递改了日期格式，所有行都会被判成非账单行而静默消失**，钱一分不剩却「导入成功」。补一条硬要求兜住：**全部数据行都被判为非账单行时必须报错**，文案要说清「N 行的账单日期都读不出来，请检查解析规则里『账单日期』映射到哪一列」——**不许复用 Z15 那句「上传文件为空」**，那句话会把人指向完全错误的方向（文件明明有几十行）。

`§5.2` 里那句「批次行数永远等于文件行数」就此改口为：**等于文件的数据行数，不含非账单行**。

## 对账是一整块，结果合成一行写进批次备注

「对账」包含两半，**写在一起**：

1. **合计行三项**：件量 = 数据行数、合计行重量 = Σ账单重量、合计行费用 = Σ账单其它费用。**面单费不在快递的合计行里**（那是本公司按快递公司配置的固定单价），所以整票运费对的是「合计行费用 + 面单费 × 件量」，备注里要把这个反推数也写出来，让人一眼能核。
2. **账单与订单的匹配结果**：已匹配 / 重复 / 虚假 / 重量省份异常各多少行，外加被跳过的非账单行（行号 + 重量 + 费用），让人看出少了哪几行、少的是不是真钱。

**汇总对不上时不拒绝导入**：照样入库，提示一句 + 写进批次备注。

这与 §15.4 的负数闸（数值为负就整份不落库）**方向相反**，是有意为之：账单是快递给的唯一事实来源，把它挡在门外连异常行都没法处理，人只能回去求快递重发文件。代价说在明处——**一个「对不上」的批次照样能一路走到确认，拦人只靠批次详情里那一行备注，没有弹窗、没有门禁**。之所以还可以靠那一行备注兜着：合计行本身就在文件里，对不上时差值、行数、每行金额全都在，人看得出是不是真少了钱。

> **对账两侧必须同一把尺（2026-10-29 决议 AG3，见 ADR-0039 与设计文档 §21.2）。** 本文首段那句「合计行重量 = Σ账单重量」预设了两侧是同一个数，但当时账单重量与账单其它费用在解析时都不量化：内存里带原精度，落库才由数据库舍入。于是备注写的是**文件原值**的求和，人拿去跟界面/库里的行核对时对不上，看起来像系统算错；合计行自己那一格同样不量化，「合计 == Σ行」那句比较里两侧各走各的方向，会报出一条纯由舍入差造成的「不一致」。现在 `账单重量` 在读格子时就整到 3 位、`账单其它费用` 整到 2 位，**非账单行（合计行）的那两格同样处理**——它是核对基准，不同尺就白核一次。代价写在这里：真实的合计行差异会比以前更早暴露（以前被两侧不同的舍入掩盖掉的分位差会显出来），那是多一条核对提示，不是错数。
