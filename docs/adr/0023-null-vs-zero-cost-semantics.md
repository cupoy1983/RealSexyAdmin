# 用 NULL 与 0 区分「缺失成本」和「有意0成本」

成本价为空(NULL) = 缺失，标「待补充」触发人工补录；成本价显式为 0 = 有意0成本（配件、邮费占位），正常不报缺失。放弃了加「是否计成本」布尔字段或字典类型的方案，因为「录入必填、配件显式填0」的纪律已足够，且自带纠错——谁忘了填留空就会被揪出来，比多维护一个标记字段更简单。

> 2026-10-24 扩展：同一套空值语义现在也用在**编码列**上，含义是「无规格」而不是「缺失」。`ecommerce_sku_cost.sku_code`（规格商家编码）与 `ecommerce_order_detail.sku_code` 一并放开可空，NULL = 该商品没有规格之分；不用空串，因为 `ecommerce_sku_cost.sku_code` 上挂着唯一索引，MySQL 唯一索引不约束含 NULL 的行——多条「商品级行」能共存，而多条空串会直接撞索引。
>
> 配套规则：主商家编码必填，规格商家编码选填，**两者不允许相同**——录入时相同就自动把规格编码置为 NULL（不报错打回），订单导入（Excel 与快麦接口）落库前做同样的归一化，因为快麦对无规格商品就是两个字段填同一个值。两个编码在新增后都不可修改，改编码等于删除重建。
>
> 匹配口径随之改成两段式：子订单的规格编码有值时按（主商家编码 + 规格商家编码）精确查成本行；规格编码为 NULL 时按主商家编码查商品级行，**且该主编码下存在规格行时一律不兜底**（同一主编码可能挂着几十个成本不同的规格，取哪条都是错数）。成本缺失判定同步去掉「规格编码为空就不算缺失」的短路，否则无规格商品会既查不到成本、又不进待补充清单。
>
> 商品级行的「同一主编码只能一条」由服务层校验保证，数据库层不设这个约束（MySQL 没有对 NULL 生效的部分索引，硬做要引入生成列，代价不值）。
>
> 存量一次性订正（2026-10-24 执行）：成本表 152 行两码相同记录 → `sku_code=NULL`（152 个主编码互不相同，实测名下都没有规格行，兜底不产生歧义）；订单明细 539 行空串记录与 273 行两码相同记录 → NULL。顺带把成本快照补齐——这批订单是成本表灌数之前导入的，5558 行明细的 `cost_price` 全部为 NULL、3774 张主订单的发货成本合计全部为 0，等于成本层还没落地过：按新口径回填后有价 2395 行（规格级命中 2279 + 商品级命中 116）、命中成本行但成本价为空 63 行、查无成本行 2561 行（这 2624 行留 `cost_missing`），539 行占位明细不判缺失；1873 张主订单至少有一条有价明细，其中汇总实际变化并刷正的是 1819 张（另 54 张的实发与实退都为 0，重算后仍是 0）。订正后逐行回读校验全部对上。此后主表调价靠「更新订单」重算，不再手工补数。另有 539 行「编码与商品名称皆空」的订单明细，按业务判定属于非 ERP 发货的占位行，明确**不进**成本缺失清单——代价是这部分已付金额对应的商品成本恒为 0。

> 2026-10-25 两条落地缺陷的修正是这套语义的直接后果，不是新决策：
>
> - **「NULL=缺失」必须写得回去**。框架的 `CRUDBase.update` 收到 Pydantic 模型时会 `exclude_none` 丢弃显式 null，于是「把成本价清空」这个动作在库里根本没有表达能力——保存后旧值还在。服务层改为传 `model_dump(exclude_unset=True)` 的 dict：提交 null 就是置 NULL，没提交的键仍保持 PATCH 语义不动。前端配套把成本价的 `undefined`/`""` 规范成 `null` 再提交，否则 JSON 序列化连键都丢掉，后端只能理解为「没改」。0 仍然照写，与 NULL 是两回事。
> - **成本行的删除改成物理删除**。「删除等于重建、编码不可改」的纪律要求被删掉的编码能被重新录回来，而 `sku_code` 上的唯一索引不认 `is_deleted`——软删的幽灵行仍占着那个编码，重建时直接撞 1062，等于把「删除重建」这条路堵死。这与账单批次作废（ADR-0033）是同一个理由、同一个写法：业务层自己下 DELETE。成本表被删的行只剩历史订单里的成本快照，没有外键指向它，删掉不影响任何已入库订单。

> 2026-10-25 同日补一条口径（这个是决策，不是缺陷修正）：**同一主编码下商品级行与规格级行不可混挂，创建期双向拒绝**。此前只有取价侧的兜底闸（主编码下有规格行时，商品级行永远取不到价），录入侧照样能把两种形态建在同一个主编码上——那条商品级行就成了永远生效不了的死记录，只会以「成本缺失」的形式出现在待补充清单里，看不出原因。现在规则是：一个主编码下的成本行只有两种合法形态，**全商品级（1 条）或全规格级（N 条）**；要换口径只能删除重建，与「编码不可改」是同一条纪律。取价侧的兜底闸**保留不删**：创建期校验只管得住走服务层的录入，历史数据与手工 SQL 插进来的混挂仍要靠它。存量实测混挂 0 条，无需订正。

> 2026-10-25 编码大写统一（决策，附带把三条规则正式命名）。系统里有两把比较编码的「尺子」，行为不一样：**数据库**这把不分大小写（取价命中、编码查重、列表搜索都走它，实测 `'SM037' = 'sm037'` 为真）；**「两码相同即不分规格」那句判断**走的是我们自己写的代码，逐字符比对，分大小写。快麦把同一款填成 `SM037` / `sm037` 时，那句判断会判成「两码不同」，规格商家编码原样留着，明明不分规格的商品被当成规格级去取价——精确查规格成本行查不到（库里那条是规格格为空的），按本 ADR 又不许降级——于是成本为空、进待补充清单，而且清单只写「缺成本」，人根本看不出是小写码引起的。所以：**两个编码在比对与落库前一律去空格 + 转大写**（`normalize_merchant_code`），空串归一成 NULL；只动两个编码列，商品名称与规格名称保持快麦原样。
>
> 这条不改变任何一笔钱的结果（数据库本来就把大小写当同一件事），它只是让那句 Python 判断和其余所有口径一致，把这个口子彻底关掉。实测存量 1744 行成本、5558 行明细里「两码只差大小写」为 **0 行**，即今天没有数据正在踩这个坑——这是**预防**，不是止血。含小写的存量（成本 103 行、明细 440 行）都是一串统一小写、两码本来就不同的行，判得对、取价也对。
>
> 三条规则自此正式命名，「归一化」在本项目里**只指 A**，不再混用于大小写：**A 同码置空**（两格相同→规格格落 NULL）、**B 混挂禁死**（同一主编码下商品级与规格级不可并存）、**C 编码大写**（两格先去空格转大写再比对、再落库）。
>
> 存量已一并刷平（2026-10-25 执行）：成本表 103 行、订单明细 440 行的两个编码列 `UPPER(TRIM(...))`，先出 CSV 备份再跑，回读断言 11/11 通过——活行数、商品级/规格级行数、幽灵行数都不变，`Σ成本价`、`Σ发货成本`、`Σ退货成本` 三个合计与订正前逐字相同，证实这次订正一分钱都没动到。落地面见设计文档 §14.6。

> 2026-10-26 两条收口（Z16 / AA7），都不改变本 ADR 的 NULL-vs-0 语义，只是把入口收紧：
>
> - **成本价不得为负**。`SkuCostCreateSchema`/`SkuCostUpdateSchema` 的 `cost_price` 加 `ge=0`——实测原来传 `-5`、`-0.01` 都能 200 落库，负单价会顺着「成本价 × 数量」把发货成本算成负数、把利润抬高。**`0` 继续合法**，这正是本文开头那条「NULL=缺失、0=有意 0 成本」的纪律，不许借收紧时顺手把 0 也禁掉。同口径扩到导入：Excel 里实发数量、实退数量为负 → **整批中止报错**（不做「跳过那一行」），间接成本明细（该子域还没编码）将来实现时照此加校验。
> - **无规格行的「规格名称」必须留空**。规格商家编码为 NULL 的成本行，`sku_name` 只允许为空：前端输入框灰掉、后端拒绝任何非空值。有规格行的规格名称**仍然可以编辑**（只锁无规格行，不锁全表），因为它是人工填的展示文字、填错了得有地方改。这与上面规则 C 那句「只动两个编码列，商品名称与规格名称保持快麦原样」不冲突——那句说的是**不做大小写化**，这条说的是**无规格行不该有规格名称**。

> - **主商家编码 trim 后为空即拒绝创建**（2026-10-27 决议 AB2 附带修掉的真缺陷，设计文档 §16.10）。`normalize_merchant_code` 会把「   」变成 `None`，而框架 `_build_conditions` 对**值为 None/空串的条件是整条丢掉**的：下面那句「这个主编码下有没有成本行」的查重于是退化成「随便哪个主编码下有没有」，既能把别人的记录算到这条头上，也能让编码为 NULL 的成本行真的建出来——而 NULL 主编码在两段式取价里谁都命中不了，等于一条永远参与不了算账的垃圾行。所以空主编码必须在查重**之前**就拒掉，文案「创建失败，主商家编码不能为空（纯空格也算空）」。`sku_code`（规格编码）仍然可以为空，那是「无规格」的合法表达，别一起禁掉。

> **「没填」与「读不出来」是两件事（2026-10-29 决议 AF2，设计文档 §20.2）。** 本 ADR 这套 NULL-vs-0 语义有个前提：这一格**真的没填**。而订单导入里 `重量kg(SKU)`、`成本价(SKU)`、`系统实发成本`、`实退成本` 与两个数量列原先走的是「认不出就当没填」——一格写成 `45,6kg`、`待补` 会静默变成 NULL（成本/重量）或 0（数量），脏值被本 ADR 的语义**吸收成「缺失」**，界面上没有任何一处说第几行坏了；同一份文件的买家已付/退款/运费收入撞上非数值却会报错，两套态度。现在并成一把尺：空值与占位符（`-`/`--`/`/`/`无`/`暂无`）照旧是「没填」，其余读不出的一律**带行号报错、整份不落库**。
>
> 这不改变 NULL 的含义，只是把 NULL 的来源收窄成「真的没填」——否则「缺失」这个信号本身不可信，而整套人工补录纪律都建立在它上面。账单侧 `_soft_decimal`（非账单行上的数值格子）那处**故意保持宽松**，不受本条影响：非账单行本来就不入库、不算钱。

> **本文开头那句「成本价显式为 0 = 有意0成本」第一次被业务方点名确认——但到今天仍未落进库里（2026-11-08 决议 AP1，同天两次收口：「1不跑」+ AQ2「NLPJ 的成本先不管了」，业务方原话「NLPJ就是0成本，对的。」，设计文档 §27、§27.7）。** 它一直只是一条纪律，库里从没兑现过：实测主表 1744 行里 `cost_price = 0` 的**一条都没有**，290 条「看起来没价」的全是 NULL——连例子（SKU 8888 邮费占位）都在表里查无此行。
>
> 这次的值是 `NLPJ` 系列 13 行主编码：它们对应快麦「出库单」那批订单明细（9 行，店铺编码 `0`）。主表这 13 行的 `cost_price` 一直是 NULL，于是 9 行明细被判成「缺失成本」、挂进「待补充成本」清单——清单传递的暗示是「这单有成本、你还没填」。业务方对这一批的原话只有一句「**NLPJ就是0成本，对的。**」：答案是 `0`，不是「还没填」。为什么是 0 他没有说，本 ADR 也不替他补一个理由。
>
> 所以这次订正同时动两侧，缺一侧都是半修：主表 `NLPJ%` 那 13 行 `NULL → 0.00`（这是「0 = 有意」的入口），订单侧 9 行明细 `cost_price → 0.00` 并把 `cost_missing → 0`（这是它应当产生的结果）。`computed_product_cost` 与主订单的发货成本合计**一列都不用动**——`0 × 数量 = 0`，本来就落在 `0.00` 上，这也是当初「9 行 UPDATE + 主订单聚合重算」那份方案在 AP1 之后缩水成两列的原因。SQL 见设计文档 §27.3；这份 SQL 同日被业务方定为不跑（原话「1不跑」，理由未给，§27.5），**同日 AQ2 进一步收口：「NLPJ 的成本先不管了」——SQL ①② 两段一起作废，既不脚本刷，也不手工在界面填价、更不填 0（§27.7）**。于是库里今天仍是原样——那 13 行 NULL、`cost_missing=1` 仍是 2604 条，「0 = 有意」这条口径处于**已确认、不做动作**状态（口径本身没被撤回，只是这一批不落地）。**钱不受这件事影响**：这 9 行本来按 NULL→0 计，`computed_product_cost` 与主订单聚合都躺在 `0.00` 上，翻不翻语义算出来是同一个数；受影响的只有「待补充成本」清单里那 9 行读起来像「还没录」。编码 `0` 那家店的平台是另一件事，与成本无关，AQ1 已定为留「快麦」（见 ADR-0024 与设计文档 §27.7）。
>
> 反面要说清：这次不是「NULL 判错了」。`NULL = 缺失` 这套语义一直成立，缺的是录入那一步；把 NULL 一律改成 0 来「消清单」才是破坏这套语义。所以将来真要订正也只能按 `NLPJ` 前缀点名，其余 277 条 NULL（290 − 13）一个都不许碰——SQL 不跑不等于这条纪律松了。
