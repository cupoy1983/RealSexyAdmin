# 考勤组剔除与考勤同步互斥

钉钉考勤月报同步的三条规则，以及它们为什么会是现在这个样子：

1. **没有考勤组的人不产生考勤数据** —— 同步时先判定，没考勤组就跳过，且把历史空壳清掉；
2. **整批同步要么全成、要么全废** —— 任一人失败整批作废，不留半成品；
3. **手动拉取与自动任务互斥** —— 同一个月谁先跑谁生效，不会被拉两遍。

> 2026-10-30 建立，结论来自一轮 grill（A1–D1）。
> 起因：考勤统计里出现了测试用户的两条**统计列全 0** 的月报 —— 那人在钉钉里
> **不属于任何考勤组**，钉钉根本不会给他考勤数据，同步却照样给他建了空壳行。
>
> 2026-11-06 修订（缺陷复核 BUG-01，用户 A1 拍板）：整批原子提交不变，但
> **「库里有数据 = 拉全了」这个前提已失效** —— 离职预同步走 `sync_month(user_ids=...)`
> 只写指定人员的月报，属于合法的部分同步。
>
> 2026-11-06 二次修订（独立复核严重 1）：先改成的「人数核对」仍有漏洞 ——
> 离职员工的历史月报会顶替新进考勤组但还没同步的人。最终口径改为
> **「应到人员名单 ⊆ 当月有月报人员名单」**（比集合，不比数量），见第二节。
> 原被否掉的「分子/分母」思路因此重新启用，同步记录表仍未采用。

## 一、三条规则怎么来的

### 没有考勤组就不该有考勤数据

考勤组（不是部门）来自钉钉 `topapi/attendance/getusergroup`，按 userId 反查这个人属于哪个考勤组，
一个员工只属于一个。取不到 = 他不在任何考勤组里 = 钉钉不会给他出考勤结果。

同步时若不提前挡住，就会写出一整行「应出勤 0、出勤 0、迟到 0…」的空壳月报，
页面上看起来像是这个人整月旷工，实际是数据不该存在。

**判定必须在拉数据之前**（A1/B1）。`getcolumnval` 是按人按月打的接口，
不在考勤组的人打过去也是白打，跳过还能省下这些请求。

### 空壳要连根清掉，不能只藏

跳过只管住新数据，历史已经写进去的空壳没人删就会一直堆着。
所以同步碰到没考勤组的人时，顺手把他**所有** `group_id IS NULL` 的月报行 + 对应日明细**物理删**掉。

日明细必须跟着删：月报没了、明细还在就是孤儿，查看明细弹窗还能把它们捞出来。

### 「接口失败」和「真的没有」必须分开（A1）

这是整套逻辑里最要命的一条。`getusergroup` 原来不管**接口报错**还是**真的没考勤组**，
都返回同样的 `{"group_id": "", "name": ""}`，上层用 `if group.get("name")` 一挡，两种情况同样不更新快照。

混在一起的后果：钉钉抖一下 → 有考勤组的人被误判成没有 → 顺着就把他的考勤数据清了。

现在改为：

| 情况 | 处理 |
|---|---|
| 接口 errcode 非 0（或网络问题） | `get_user_group` **抛异常**，上层不接，让整批作废。「有没有考勤组」未知时不能当成没有 |
| 接口通了但返回空 | 真的不在任何考勤组 → **清空**快照 + 剔除数据 |

配套地，`_refresh_binding_snapshot` 里的考勤组快照**不能再「取不到就保留旧值」**了
（工号、部门名仍保留旧值，它们只是报表前缀列）。否则人从考勤组被移出去后，
绑定表里的 `group_id` 会一直挂着旧值，永远判不出「他现在没有考勤组」。

## 二、整批原子提交仍然成立，但「有数据 = 拉全了」不再成立

`sync_month` 循环里原来有单人 `try/except`，10 个人挂 3 个也会留下 7 行半成品。
现在**刻意不吞单人异常**，让它冒泡出去，由调用方的事务回滚兜住：

- HTTP 接口：`db_getter` 本来就是请求级事务（`async_db_session() as session, session.begin()`）；
- 定时任务：`insert_dingtalk_monthly_report_job` 里同样是 `async_db_session() ... db.begin()`。

代价与收益：

- 任一人失败 → 整个月一行不留 → 可以被重拉；
- 原子提交依然保证「一次同步内部不留半成品」，但它**不能证明全公司所有人都进了这次同步**：
  离职预同步只传 `user_ids`，一次只写几个人的月报，同样是一次完整成功的原子提交。
  因此 `month_synced()` 不能再只做 exists 查询，改为人员集合核对（见下）。

**2026-11-06 最终判定口径**：`应到人员名单 ⊆ 当月有月报人员名单`。

- 应到 = `iac_account_binding` 中未软删、OA 用户启用且未软删、已绑定钉钉、
  `group_id` 非空的 `oa_user_id` 集合；
- 已到 = 该月未软删月报中，属于应到名单的 `oa_user_id` 集合；
- 应到名单为空时直接判「未同步」；只有应到名单被已到名单完整包含才算拉完。

只比数量会漏人：B 离职 + C 新进组时，B 的历史月报仍在库里，行数刚好等于应到人数，
系统却会误判 C 的考勤已拉完。分母随人员进组 / 离职自动变化，无需迁移、无需同步记录表；
离职软删绑定后不再计入应到名单，其历史月报保留不影响判定。部分同步永远集合不全，
全量补拉照常进行。

自动任务只拉上个月、不回头补历史月份，所以「拉了一半」本来就无法补救，
整批作废反而是更诚实的状态。

## 三、自动与手动互斥（C1/C2/C4）

- 手动和自动**都固定拉上个月**，不做任意月份的选择（C1/C4）；
- 上个月库里已有数据、且应到人员全部有月报 → 判定为已拉过 → **按钮不显示、自动任务直接跳过**（C2）；
  只有部分人员预同步的数据 → 仍判定未拉过，按钮保留、自动任务照常全量补拉（2026-11-06 修订）；
- 页面按钮的显示条件是 `can_sync = 已到每月 3 日 00:00 && 有可拉的人 && 上个月还没拉过`。
- **2026-11-03 修订**：自动任务改为每月 3 日 00:00 执行；手动补拉也只在这个时点之后开放。
  管理员设置上月绩效时若发现上月无考勤，也允许在同一时点之后自动补拉。
  完整时点和钉钉通知规则见 ADR-0012。

「有可拉的人」= `iac_account_binding` 里未软删、**`group_id` 非空**的人数 > 0。
一个都没有的话，拉了也拉不出任何月报（没考勤组的人会被跳过），按钮显示出来只会让人白点。

后端 `/internal/attendance/sync` 再做一次同样的校验，防止绕过页面直连接口重复拉。

## 四、被否掉的方案（记录理由，别再捡回来）

| 方案 | 为什么没采用 |
|---|---|
| 新建 `iac_attendance_sync_log` 表记录每次同步 | 用户否掉。**2026-11-06 复核仍不采用**：部分同步出现后改用「人员集合包含」即可判全量，无需新表与生产迁移 |
| 用分子/分母（有月报人数 vs 有考勤组人数）判定拉没拉全 | 原以「拉不全就整批失败、中间态不存在」为由作废；**2026-11-06 前提失效后重新启用**（合法的部分同步就是中间态），见第二节 |
| 程序自动剔除用软删 | 用户选物理删。空壳行本来就不该存在，没有保留价值 |
| 历史月报按人当前状态一起清掉（乙案） | 考勤是既成事实，人被移出考勤组不该抹掉他上个月的考勤记录 |

## 五、代价与边界（知道就好）

- **新加考勤组的人会晚一个月才有数据**。绑定表的 `group_id` 是上次同步时的快照，
  本月新被加进考勤组的人，这轮分母里没有他。
- **所有人都没考勤组时**，同步跑完不写任何行 → 判定为「没拉过」→ 按钮仍显示。
  有「有可拉的人」这条兜底在，这种情况按钮也不会出现。
- 删除 OA 用户时的考勤预同步（`_sync_attendance_before_dismiss`）仍保持
  **尽力而为**：整批作废只记 warning，不阻断删除（离职不可逆，不能因为考勤没存下来就不让删人）。

## 八、首次同步死锁（2026-11-05 修复）

### 现象

全新部署后，考勤统计页的「拉取上月考勤」按钮**永远不显示**，即使员工已在钉钉加入考勤组。

### 根因

`has_group_member()` 判定的是绑定表 `iac_account_binding.group_id IS NOT NULL`。
但这个字段**只在同步成功时由 `_refresh_binding_snapshot` 写入**。

于是形成死锁：

```text
从未同步过 → group_id 全为 NULL → has_group_member=False → 按钮不显示
          → 永远无法首次同步 → group_id 永远为 NULL
```

同步逻辑本身并不依赖这个字段：`sync_month` 取**全部**钉钉绑定用户，
再逐个调 `get_user_group` 判定，没考勤组的跳过。
也就是说「能不能同步」和「按钮显不显示」用了两套不一致的判定。

### 修复

`has_group_member()` 改为「存在已绑定钉钉的用户」，不再读 `group_id`。
考勤组的真正判定仍在同步时进行，不在按钮这一层重复挡一次。

### 边界

- 若所有员工都没加考勤组，按钮会显示，同步结果全部为 skipped，不产生空壳月报，符合预期。
- `group_id` 仍由 `_refresh_binding_snapshot` 在同步时回写，逻辑不变。
- 该字段现在只作为**已同步结果的快照**使用，不再承担「能否同步」的前置判定职责。
