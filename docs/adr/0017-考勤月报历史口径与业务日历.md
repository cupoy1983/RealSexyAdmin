# 考勤月报历史口径与业务日历统一

> 2026-11-09 建立。来自复核报告「功能缺陷 1 / 4」与 A4、A8、A9 拍板。
> 状态：设计已拍板，文档先行；2026-11-09 代码与回归测试已落地。

## 一、考勤月报是历史事实（A8）

- 月报列表按月份展示当月所有人，**不按当前用户状态过滤**：已停用（`UserModel.status = 1`）、
  已软删（`is_deleted = true`）的员工照常显示。ADR-0007 第六节已确认软删行 INNER JOIN 仍查得到，
  这不是 bug，是有意保留的考勤历史。
- 复核报告「功能缺陷 4」说的不一致，真因不是「多显示」，而是列表里**没有状态标记**：
  补「在职 / 已停用 / 已离职」标记字段（响应结构 + 前端列）。
- 保留 `group_id IS NULL` 空壳行剔除（ADR-0008）。
- 正式工资条与绩效的人员口径仍是「账号启用且未软删」（ADR-0011 修订 2）。
  两处口径不同是**有意的**：月报记历史事实，薪资记当月结算范围；离职员工改由 ADR-0016 离职结算单承接。

## 二、业务日历统一到服务端（A4）

- 复核缺陷：`SalaryPerformanceTab.vue` 的 `previousMonth()` 用 `new Date().getMonth()` 直接当上个月，
  一月会得到 `YYYY-00` 且年份不回退；`MonthlyReportTab.vue` 的 `defaultMonth()` 跨年算法是对的，作为对照。
- 修复：默认「上个月」与「每月 3 日后开放」都由**服务端**给出（服务器日期、上个月、是否开放），
  两个 Tab 不再用浏览器本地日期自己算；后端 `date.today().day < 3` 硬闸保留，前端禁用仅作提示。
- 实施形态：`GET /internal/salary/business-calendar` 返回服务端 `today`、`current_month`、
  `previous_month`、`performance_open`。前端两个 Tab 首次加载各取一次，取不到时月份留空、
  「登记 / 确认」按钮禁用，不再自行用 `new Date()` 推算。
- 后端 `SalaryService.previous_month()` 与 `MonthlyReportService._previous_month()` 已经是
  「当月 1 日减一天」的正确算法，不需要改算法，只需要把结果交给前端。具体接口形态属实现细节，在实现阶段定。

## 三、停用边界（A9）

- 停用（`set_available()` 置 `status = 1`）**不触发**离职结算：停用可逆，不是离职；
  停用员工仍在册、考勤照常同步、月末照常参与正式工资条。只有删除用户（离职联动）触发 ADR-0016。

## 四、被否掉的方案

- **月报列表也按用户状态过滤**：历史月份会凭空少人，与 ADR-0007 第六节冲突，被否。
- **只修一月跨年、3 日闸继续用浏览器本地日期**：客户端时间可改，前后端两套日历长期不一致，被否。
- **停用时也生成离职结算单**：与「停用可逆」冲突，被否（A9）。
