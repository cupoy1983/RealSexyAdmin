# 分销订单：商品成本的第二个来源，与运费侧的彻底摘出

标签里带 `已生成采购单` 的那批子订单，货是 1688 上的其他商家发的，不是我们公司发的。于是两条口径同时被打破：**商品成本不从系统 SKU 成本表取，运费也完全不参与匹配与摊分**。这是 ADR-0022「系统 SKU 表是商品成本唯一事实来源」的**第一条例外**，也是 ADR-0034「运费回写只认 ERP发货子订单」的第一次收窄。

## 判据只有一条，而且不是最直觉的那条

Excel「订单标签」列（快麦第 13 列，实测版式见 ADR-0038）的内容**归一（去空格、全半角）后子串包含 `已生成采购单`** → 这条**子订单**是分销订单。不做全等比较，不看其它字样。

2026-10-28 拿一份真实导出（`12345.xlsx`，144 行含末尾汇总行）实测过为什么不能用「分销订单」四个字：

| 尺子 | 命中行数 | 这些行的事实 |
|---|---|---|
| 含「分销订单」字样 | **47** | 44 行是 `ERP发货` 且用**我们自己的圆通单号**（`YT7652…`）发货 |
| 含「已生成采购单」 | **3** | 全部是 `拼多多分销订单,已生成采购单`，运单号是 `4354…445624` 这种**非圆通号**（商家侧发的） |

快麦标签里的「淘宝/天猫/抖音/京东分销订单」说的是**销售渠道**（分销平台来的单），跟谁发货无关。真按那四个字判，44 条自发货订单会被错摘出运费与成本两条线。**标签本身是逗号拼的多值串**（`预发货`、`韵达停发,预发货,发货前售后`），所以只能做子串判定。

## 存的是分类结果，不是标签原文

库里加 `ecommerce_order_detail.distribution_order_type`：`0 = 非分销订单`、`1 = 代拍分销订单`、`2 / 3 / 4 预留`。**明确不是 boolean**，因为业务逻辑以后要按更多分类分支走（预留位现在没有对应词，先不落）。标签原文不存——存了也没人看，而它是一份会随快麦改版而变的自由文本。

**界面不显示这一列**（列表与展开行都不加），只在处理逻辑里按它筛。

## 成本：取 `系统实发成本` 原值，不乘数量

三个候选里选了 `系统实发成本`（快麦算好的这一行总成本）：
- 不选 `成本价(SKU) × 实发数`——那是拿快麦单价再乘一遍，而我们本来就是因为不信 SKU 表才开这个例外的；
- 不选「置 0 / NULL」——那样分销订单的利润等于全额毛利，数字错得更彻底。

**同一主订单里两种口径混算**是本轮最容易被误读的代价：非分销走「SKU 成本表 × 数量」，分销走「快麦原值」。而这两个数在真实数据里就是不等价的——同一份样本里出现过 `实发=1、成本价=8.5、系统实发成本=9.0`、`实发=50、成本价=4.18`（乘算 209.00）而 `系统实发成本=208.98`、`0.0456 → 0.05`。所以「利润对不上快麦汇总行」不再等于「有 bug」。

三条配套口径：
1. **`cost_price` 也来自 Excel**（取「成本价(SKU)」原值，2026-10-28 业务方纠正：「分销订单的 cost_price 是由 excel 里面来的」）：这一行**根本不查 `sku_cost` 表**，与 AC16 的原话「成本不从sku成本表里面获取」字面一致。此前本条写的是"照旧回查主表存快照、只是不参与算成本"——那是把"不参与算钱"当成了"可以留主表的数"：它既不参与任何计算，又会在界面与导出里让人误读成"这行的成本按我们自己的成本表定过"。既然不是从主表查的，**不置 `cost_missing`**、**不进「待补充成本」清单**也就顺理成章——成本来自 Excel 原值，SKU 表里没有它是常态，报成"缺成本"是把 1026 行量级的正常数据刷成警报。
2. **不跑「SKU 表算出的成本 vs 快麦原值」的差异告警**——既然已经说了不从 SKU 表取，再报"两边不一致"只是噪音。
3. `系统实发成本` **空着或为 0 就照原值落 0**，不告警。代价：这一行利润偏高。实测这份样本里 `系统实发成本` **一格空的都没有**，三条分销行是 `7.72 / 3.56 / 7.72`。
4. **两个计算成本同一个口径**：`computed_product_cost` 取 `系统实发成本`、`computed_return_cost` 取 `实退成本`，都取快麦原值、都不碰 SKU 成本表（2026-10-28 业务方原话：「分销的退货成本和发货成本是一样的，我们自己没发货数量，怎么会有退货数量呢？」）。分销订单不是我们发的货，也就不会有退货——实测那三条分销行的 `实退数量` 与 `实退成本` 都是 `0`，所以这条统一口径**不改任何数字**，只是不把"例外"半开：留着「退货成本按 SKU 价 × 数量」等于一行里两个成本来自两个我们说了不算不成立的地方。

## 运费：整条线摘干净

分销订单**不参与运费匹配与摊分**，也**不进「只看缺账单」筛选**。改动就是两处查询各加一个条件：账单侧找 ERP发货子订单的那条，和订单侧 `freight_missing` 那条。

> 2026-10-30 AK 轮补充：订单侧那条尺子现在只住在一个地方——`order/crud.py` 的 `missing_bill_conditions()`，主订单列表的 EXISTS 与批次确认前的缺账单计数都套它；入口也只剩订单列表搜索栏一个（设计文档 §24）。本文的判据本身一个字没动，分销行照样排除在外。

为什么不留在里面（这是本轮唯一被数据翻过来的判断）：
1. 那 3 行**是 `ERP发货`**（`is_erp_shipped=True`），照现行口径会被拉进匹配。可它们的单号是商家侧承运商的，**永远不可能出现在我们的快递账单里**，`freight_cost` 就永远是 NULL。今天库里 4318 条 NULL 是因为一份账单都没导入；等账单导完，这个筛选里剩下的本该都是"真缺账单"，分销行会常年混在里面分不清（按样本比例约 2%，一个月一百多条量级）。
2. **号撞上就会记错钱**，概率低但方向是错的：1688 商家用的承运商可能正是我们月结的那家，一旦某个代发单号出现在我们账单里，这条分销子订单就被当**原件行**参加摊分——一笔我们根本没付的运费进了成本，而且同票真发货那几条分到的份额变少（整票按权重切，多一条就少一份）。

**乙的代价明确接受**：如果哪天分销订单其实是我们自己付的运费、账单里真有这个号，这笔运费会被**静默不算成本**（运费偏低、利润偏高）。拦不住，只能在核对时记得分销单不参与运费。

`其他ERP发货` **不能当判据**（同一条数据翻出来的反面）：它与分销是"同一种类型"，但那批订单不是通过快麦下单的，根本不带标签，用它会漏。而且它今天已经是 `is_erp_shipped=False`、`实发数=0`（9 月样本 1026 + 43 行无一例外），本来就没有"发货的商品成本"可言。

## 更新与存量

- **订单更新时这一列跟着新标签走，值没变就不写**（扩 §5.1b 第 5 步的子订单更新清单一项；与 Z3「主订单那 9 列不再扩」不冲突）。
- **存量不回填**：库里已有的 2026-09 那 5558 条**全部落 0**（那份导出根本没有标签列）。需要按某个月的真实标签刷时，由业务方明确提出、按 `订单商品明细ID` 走数据订正脚本，**系统不主动猜、也不给界面编辑入口**。
- **列是 `INT NOT NULL`、库里没有 DEFAULT**（`default=0` 只写在 SQLAlchemy 侧，建表时不会变成 `DEFAULT 0`）。走导入/更新路径没影响（ORM 一定带值），但**手工用 Navicat 往 `ecommerce_order_detail` 插行必须自己填这一列**，否则报 `Field 'distribution_order_type' doesn't have a default value`。

> **2026-10-29（AF1，设计文档 §20.1）：分销刷回非分销时，「缺不缺成本」这个标记必须自己站得住。** 翻转后的那条子订单成本改回按 SKU 主表重算，而 `cost_missing` 原先写在「成本价这一列碰巧变了」那个 `if` 里面——库里 NULL、主表也查不到时 `NULL != NULL` 不成立，整段被跳过，这一行**按 0 成本进利润却永远不进「待补充成本」清单**（清单正是按 `cost_missing=true` 筛的）。AC 那轮只测了「翻转后主表查得到价」这一半，另一半是漏网。现在这句求值无条件执行、只在值变了才写库（理由与代价见 ADR-0032 末段）。**上面第 1 条「分销不判缺失」的口径不变**：`新缺失 = 有主编码 且 取不到价 且 非分销`，分销那一侧仍然是 `False`。

> **2026-10-29（AF5=甲，设计文档 §20.4）：分销行的「成本 = 快麦原值」从此是逐字相等。** 上面第 4 条说的取原值，实现里是「原值再按见位进分落一次」——源值带小数第 3 位时，落库的成本会比那一格原值多 1 分，「取原值」这个说法就不成立了。AF5 把 `系统实发成本`/`实退成本` 这两列本身改成按四舍五入整到分（它们是快麦报过来的既成事实，不是我们乘出来的钱），进到这一行的源值已经是分精度，再走一次进分是恒等变换。代码里 `_ceil_cent(...)` 那两处调用不动，行为随输入自然收敛；口径没变，是「取原值」这句话现在终于名副其实。实测这四列在真实导出里没有第 3 位小数，所以不改任何存量数字。
