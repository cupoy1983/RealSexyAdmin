# 导入批次是订单与账单共用的确认单位，未确认不进利润

订单和账单都是「一整个月的一个 Excel 文件」，但两者入库后都需要一段人工处理期（核对异常、补成本、等迟到数据），而利润计算必须知道这批数据是否已经处理完。因此给两类文件引入同一张**导入批次表**，批次是人工确认的单位，也是利润模块的准入门槛。

**批次号是拼出来的固定字符串，不是随机号**：`order-2026-09`、`bill-yto-2026-09`，由「文件类别 + 子类别 + 月份」三段确定，批次号上唯一索引。这么做的直接后果是「同一快递类型同一月份只允许一个批次」由数据库兜住，而不是靠代码记得去查。之所以不用数据库自增 id 或 uuid 当批次号，是因为 MySQL 的唯一约束对 NULL 列不生效（订单批次没有子类别，账单批次才有），用可空的组合唯一索引会留下重复插身的口子；把「同类别+同月唯一」这个约束编码进一个非空的派生字符串，是最省事且能被数据库强制的写法。代价是批次号可读但带业务语义，将来若要允许同月多次导入，得改拼法而不是改索引。

**订单导入与账单导入共用一个「月份」列**，语义随文件类别而变：订单批次填的是**发货月份**，账单批次填的是**出账月份**。合成一列而不是两列，是因为任一类别永远只用其中一个，两列会有一半恒空、且查询时容易填错。

**只有导入建批次，更新不进批次**。订单更新时若发现库里没有的新订单，归到「所选发货月份」对应的那个批次（`order-{月份}`）——同一批次就等于同一发货月份、也就是一批订单；**该月还没有批次就整份拒绝更新**，提示先用导入建批次。更新既不新建批次也不改挂已有批次。这样批次号始终唯一且可复现，不会出现「同一个月的账单散在两个批次里、确认状态各管一半」。

> **「更新不新建」是 2026-10-20 补的收口**（原写的是「不存在则自动建一条未确认批次」）。自动建等于开了一条绕开「可导入月份窗口」给任意月份建批次的通路：窗口的护栏只在导入弹窗的控件上，接口不拦窗口，只要更新还能顺手建批次，护栏就白设。代价是「这个月没有新订单、只想订正老单」也过不去，得先建批次。
>
> 2026-10-29 注：上一句里「窗口只在控件上、接口不拦」讲的是**导入入口**的护栏该由谁承担，仍然成立；但同批另有「查询也不受窗口限制」这层意思，已被搜索栏的**可查询月份窗口**推翻，见文末修订块。
>
> **账单侧仍不提供更新，但「重导只能先订正数据库」这句已经过期**：未确认的账单批次现在可以在界面**作废**，见下条。

**批次作废：未确认的账单批次可以整批物理删除**（2026-10-20 新增，权限点 `module_ecommerce:batch:delete`）。导错了账期、选错了快递类型，过去的唯一出路是开发改库——行级删除只允许删虚假/重复行，删完还剩一堆判对了的行占着 `bill-{类型}-{月份}` 这个唯一批次号，同月同类型重导必然撞索引。作废就是把这条批次连它名下**全部账单行**一起**物理删除**，删完同月同类型能直接重导。范围有三道边界：**只有未确认批次可作废**（已确认的一律不动，与「确认即终态」一致）；**只有账单批次可作废**，订单批次不提供这个入口，重导订单仍走手工清库；作废不可恢复。

> 为什么必须写业务代码而不是复用框架的删除：框架 `CRUDBase.delete` 是**软删**（`update ... set is_deleted`），而批次号、账单行的唯一索引不认 `is_deleted`——软删掉的行仍然占着索引，重导照样撞。所以作废端点自己发物理删除语句先删账单行再删批次行。同理，订单表那几条唯一索引（`system_order_no`、`source_detail_no`）也让「软删订单后重导」走不通，这正是订单批次不开作废入口的原因：开了也只是把清库的活儿换个地方做，还多一个误删整月订单的按钮。

**「本月无账单」靠声明零行批次，不靠改门禁**。确认订单批次时要求该月**每一个启用中的解析规则**（`status=0` 且未删除的账单类型）都已有账单批次且全部已确认。某家快递这个月压根没出账单，过去是静默放行（查不到未确认批次就当作齐了），现在要人工过一道：门禁不过时一次性返回两份清单合并呈现——① 已存在但未确认的账单批次；② 本月完全没有批次的类型。对②勾选声明后，由声明入口（权限点 `module_ecommerce:batch:declare`）为这些类型生成**零行未确认批次**，再在批次列表里**逐条**点确认（不做「弹窗一次勾完」）。零行批次没有异常可处理，直接确认即可。

> 这条口径选的是「补数据」而不是「补判断」：不加 `is_declared` 之类的列、不做定时预建、不在门禁里写「允许某类型缺席」的白名单，而是让「本月无账单」这件事以一条真实的、`row_count=0` 的已确认批次存在。批次表因此仍是「这个月哪些数据进来了」的唯一事实来源，靠 `row_count=0` + 备注就能认出声明批次，代价是操作员要多点两次（声明、逐条确认）。

**确认是翻状态 + 回写，而不是把数据搬到别的表**。导入时数据直接以「未确认」状态落库，人工筛着处理完点确认，确认动作在一个事务里翻批次状态并完成运费回写。之所以不在导入时就完成回写，是因为账单里的异常（虚假、重复、重量省份不符）必须先由人判完，用未判定结果算成本等于把错误直接写进利润；也不选择「先落临时表、确认后才转正」，那会让查询、页面和迁移都多一份表，收益只有形式上的干净。

**门禁顺序是账单在前、订单在后，且严格同月**：要确认 `order-2026-09`，该月**每一个启用中的账单类型**都要有 `bill-*-2026-09` 且全部已确认——没有的要先走上条声明。账单处理慢是常态，所以宁可让 9 月底发货、10 月才进账的运单先按「还没定」出列，等 10 月账单来时用覆盖式回写补上（见 ADR-0034），也不让订单批次一直卡在未确认、把利润整体拖住。结算时不再单独问「这个月的账单上传了吗」，而是问「这个月的批次都确认了吗」——批次确认成为数据齐全度里唯一需要判定的事实，其余上传痕迹都退化为过程记录。

**已确认即不可变，不支持反确认**。批次确认后其数据一律不动，订正只能直接改数据库；订单更新遇到已确认的目标批次直接拒绝。理由是确认状态一旦被撤回，利润表里已经产出的数字与数据库当前值会同时存在两套解释，而团队规模下没有精力维护「确认/反确认」的审计链，宁可把订正成本压到只有能改库的人能做。代价是操作员点错只能求助开发，明确接受。

> 「订正只能改数据库」的范围在 2026-10-20 缩小了：它现在只管**已确认**的批次和**订单**数据。**未确认的账单批次**不需要改库——作废重导即可（上上条）。未确认的订单批次仍然没有删除入口，重导订单仍要先手工清库。

订单批次确认时对成本缺失只做**软提示**（「本批还有 xxx 单成本缺失，确认吗？」）而不硬拦，因为缺失成本的订单其收入与运费都是真实发生的，让整批卡在缺失上会把当月利润整体拖住；这与 ADR-0023 把「缺失成本」标记出来交人工补录的口径一致——标记和提示负责暴露问题，不负责阻断流程。

> **规则表为空 = 拒绝确认，不是「本月不需要账单」（2026-10-26 修订，Z5）。**
>
> 上文两处「该月**每一个启用中的**解析规则都已有账单批次且全部已确认」在启用集合为空时被当成了「齐了」而放行。实测：dev 库里唯一那条 `yt` 规则处于软删状态 ⇒ 启用中的规则为空 ⇒ `POST /order/confirm/order-2026-08` 在**该月一份账单都没导入过**的情况下直接返回成功。门禁的输入本身缺失时，它给出的是「无缺口」这个假肯定，本 ADR 的保护等于空转。
>
> 改法：**启用中的解析规则为 0 条时，账单批次与订单批次的确认都直接拒绝**，提示「还没有任何可用的账单解析规则，请先到「快递账单 → 解析规则」建档」。「这个月确实没有账单」的表达方式仍然只有声明零行批次一条路，**不能靠把规则删空来过关**——这与 ADR-0029 把解析规则改成无条件物理删除是配套的两件事：硬删解决了幽灵行占住 `bill_type` 建不回来，这条解决了「没有规则就没有门禁」。
>
> 同批修正：门禁预检接口 `GET /bill/gate/{month}` 原先不校验月份格式，`2026-8` 这种写法被放过并同样回「无缺口」；改为与确认接口用同一把月份校验尺。

> **「行必挂批次」升级为数据库强制，并给「查询用的月份」立了一条窗口（2026-10-29 修订，AE 轮）。**
>
> **一、两列 `import_batch_id` 改 NOT NULL。** `ecommerce_order` 与 `ecommerce_courier_bill` 的批次号列原本可空，注释与代码路径都按「必有」来写，只有 DDL 不认。收紧前只读盘过：两张表 **3774 / 2009 行，空值 0**，所以这条不需要先做数据订正，也不会让迁移卡住。为什么值得动 DDL——批次是确认与利润唯一的准入单位，一行挂不到批次就既不可能被确认、也不会有人在界面上看见它，等于静默消失；业务代码本来造不出这种行（账单行只有导入一条创建路径且批次先建后写、作废同事务连行带批次一起删、批次表对外没有删除入口），**可空的列是这条不变式唯一的漏口**，它防得住代码、防不住手工插行。所以这次改的真正收益不是修 bug，是把「手工往这两张表插行必须自己填批次号」变成数据库层面的强制。代价如实写出来：今后用 Navicat 直插这两张表不带批次号会直接报错。全项目只有这两张表带这一列，`ecommerce_order_detail`、`ecommerce_sku_cost` 都没有，改动面就是这 2 条。dev 库由后端启动的自动迁移处理；**生产环境还没上线，所以没有任何手工 DDL 欠账**——首次上线直接以 NOT NULL 建列。
>
> **二、改必填堵不住的那一种，按脏数据报警处理，不当业务状态。** 必填只保证「列里有值」，保证不了「那个值还在批次表里」——批次表被手工删掉而行没删干净，就造出「挂不到批次的行」（实测当前 0 例）。这种行按**出账月份**筛照样筛得出来，而界面上的批次下拉只列还存在的批次（压根选不到它），因此它在界面上是可见的，可见就得有个说法：列表「批次状态」列给它**红色「批次已不存在」**（与虚假/重复同一个红），门禁预检 `GET /bill/gate/{month}` 加一句「该月有 N 行账单挂不到批次」。两处都出声、口径一致；只报警不阻断——批次本身都不在了，本来就确认不了，不需要再加一道闸。**为什么不显示成「未确认」**：那等于把系统错误伪装成一件还没办完的日常工作，业务方对这一格的原话是「这样是系统错误，出现脏数据，是不允许的」。
>
> **三、账单详情搜索栏的「出账月份」新增一条窗口：本月往前十二个整月、不含本月及以后。** 这**推翻了本 ADR 与 `docs/ecommerce/CONTEXT.md` 原先的口径**（原文：「窗口的护栏只在导入弹窗的控件上，接口不拦窗口」「查询用的月份筛选器……不受它限制（受限就查不到历史数据）」）。之所以现在敢拦查询，是因为搜索栏的「批次下拉只有选了月份之后才点得动」（没选月份时那一格是个灰框占位，2026-10-29 AH1 轮由「不出现」改成了「常驻灰框」；无论哪种，那个框能长多长的唯一约束仍是这条月份窗口）——不限制月份，就等于放弃对那个框能长多长的唯一约束。往前比导入窗口（3 个月）宽得多是为了回看一整年账；不含本月及以后是因为账单最快次月出，本月压根没有账单批次；搜索窗口 ⊇ 导入窗口，凡导得进来的月份都查得到，两条不打架。**代价写清楚并且是被明知接受的**：超出十二个月的账单行在这一页既按月份筛不到、也选不到批次，只剩「运单号」精确查一票，而那批数据是**已确认**、运费已进利润的。业务方主动提出这条限制，被问清后果后仍选限死，口径是三年前的账不在日常核账范围内，真要翻走 SQL。**这条是全模块唯一会拦查询的月份窗口**：批次确认与订单更新照旧不套窗口，否则历史数据就订正不了了。

> **删空一条批次，批次自己跟着消失（2026-10-29 AI 轮补，设计文档 §22.6）**。业务方原话是那句原始需求的后半段：「如果删除这个账单，该批次没有账单了，就连批次一起删除。」**「没有账单了」＝名下没有未软删的行**（软删行留着既不参与判重也不参与摊分，但不能让它把批次撑成「还有内容」）。连带处置**复用本 ADR 的作废语义**：连行带批次**物理删除**，含软删行一起删——理由与第二段同源，`batch_no` 的唯一索引不认 `is_deleted`，软删出来的空壳批次会继续占住 `bill-{类型}-{月份}` 这个号，把「界面看着清干净了、重导却报重复」留在路上。界面**弹二次确认**并写明不可恢复；已确认批次照旧一律不动（那道闸本来就挡着删除）。
>
> 同一条决议把批次表的 `row_count` 改成**删一行减一行**。本轮最初的推荐是「不动」（它的文档语义是「导入时这份文件认下来的行数」），改口的依据是查了它露脸的地方：它是账单批次下拉那句 `bill-ZT-Freight-2026-09（500 行 / 480 票）` 的唯一数据源，不减就成了「下拉说 500、点进去只有 497」——AE 轮刚治过同一族界面假象，别再留一处。「这份文件本来有几行」不会因此丢失，它写在批次备注里（ADR-0037）。

> **认领运单号是「已确认即不可变」的一条例外通道（2026-11-05 实施，设计文档 §26.6）。** 上文「批次确认后其数据一律不动，订正只能直接改数据库」在**认领订单**这一条线上让位：一张虚假账单行（运单号在订单表里查不到）允许由人工指认、把运单号写进**已确认的订单批次**里的子订单行。放开的是**写入的资格**，不是批次的状态——批次仍是已确认、仍不能反确认，动的只有那几格「快递单号」与行上的留痕。
>
> 之所以非开不可，是快递公司的出账节奏决定的：账单比订单更滞后，**9 月底发的货常出现在 10 月的账单里，而 10 月的账单 11 月才拿到**——那时候 `order-2026-09` 早在 10 月初就确认完了。不给这条线开门，这批运费就永远进不了成本，而它是真金白银付出去的。
>
> 代价与本 ADR 的原始担忧要一起说清：「已确认」从此不再等于「那一月的数据一个字不会再变」，它只保证**订单来源数据**（金额、成本、数量）不再被系统改动；运单号这一格仍会被后面月份的账单补挂进来。之所以没有滑回"两套数字同时存在"那个坑，靠的是另外两条现成的规矩：**运费是覆盖式回写**（ADR-0034，同一票不论谁先确认都按当期原件行全集重算再覆盖，不累加），以及**触及已确认订单批次时在账单批次备注里留一行「改动了 `order-YYYY-MM`，需重算利润」**（`_note_confirmed_order_batches`）——后者是本 ADR「确认即终态」唯一保留的告警出口。**利润不会因此自动重算**，真重算等利润模块落地再定；今天那行提示只是把"哪个月被后期账单动过"留在账上。
>
> 范围严格限定在认领这一条线：订单更新、批次作废、账单行删除对已确认批次照旧一律拒绝，本 ADR 其余部分不动。
