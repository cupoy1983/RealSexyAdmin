# 删除 OA 用户联动钉钉离职

删除系统用户时，同步把该员工在钉钉侧办理离职（智能人事「确认员工离职并删除」），并软删账号绑定记录。
此前 `UserService.delete()` 只解角色岗位关联、软删用户，钉钉侧毫无动静 —— 人会留在钉钉通讯录与考勤组里。

接口选型：`POST https://api.dingtalk.com/v1.0/hrm/processes/terminateAndHandOver`（智能人事离职并删除），
而不是 `POST /topapi/v2/user/delete`。两者都能把人从通讯录移除、转入「已离职人员」，
但离职流程留下的是一条**人事口径的离职记录**，与「OA 里某人离职了」这件事语义一致。

> 2026-10-29 建立，结论来自一轮 grill（A1–A16）。过程中推翻了三条初始设想，都记在下面，别照旧稿实现：
> 1. 最初定「整批回滚」（A3/A5）——**不成立**。钉钉离职不可逆，接口没有撤销动作。
>    批量 5 人时前 3 人已离职、第 4 人失败，OA 能回滚，那 3 人却已经走了。改为「先全量预检、再逐个执行」。
> 2. 最初定 lastWorkDate = 前一天 —— 改为**离职当天**。前一天在月初删除时会落到上个月，影响上月考勤归属。
> 3. 最初定「离职原因 ID 用配置项兜底」—— 去掉。少动一个框架文件，
>    且「匹配不到就报错」比「静默用一个可能过期的 ID」安全（`setting.py` 本次不动）。

## 一、外部前提（不满足则整条链路不可用）

| 前提 | 说明 |
|---|---|
| 智能人事流程读写权限 `Hrm.Process.ReadWrite` | 与通讯录权限 `qyapi_manage_addresslist` 是**两个不同的权限点**，归在智能人事分类下；不在敏感权限清单里，无需组织管理员授权流程 |
| 企业已开通智能人事应用 | 需企业管理员在钉钉工作台开通 |
| 通讯录部门信息读权限 | 取部门主管 `topapi/v2/department/get` 用 |

**新版域名是硬门槛**：智能人事离职接口只存在于 `https://api.dingtalk.com`，
老版 `https://oapi.dingtalk.com/topapi/...` 没有任何离职能力（官方能力表里该接口版本标的就是「新版」）。
因此客户端必须同时支持两套：

| | 老版 | 新版 |
|---|---|---|
| 域名 | `oapi.dingtalk.com` | `api.dingtalk.com` |
| token 获取 | `/gettoken?appkey=&appsecret=` | `POST /v1.0/oauth2/accessToken`，body `{appKey, appSecret}` |
| 鉴权位置 | URL query `access_token=` | Header `x-acs-dingtalk-access-token` |
| token 缓存 | Redis（`RedisInitKeyConfig.DINGTALK_ACCESS_TOKEN`） | **不缓存，每次现取** |

新版 token 不缓存是有意的：为它再加一条 Redis 键枚举就要再动一次 `common/enums.py`，
而离职是低频操作，现取的开销可以忽略。这条别"顺手优化"成缓存。

## 二、操作人 optUserId 的选取链

接口只要求「本组织员工、不能是离职员工本人」，**不要求是管理员**。选取顺序：

```
topapi/v2/user/get 拿该员工的 dept_id_list
  → topapi/v2/department/get 取 dept_manager_userid_list[0]      ← 部门主管
  → 为空则向上递归父部门（A15，钉钉没定义继承规则，这是本系统的产品口径）
  → 一路到根部门仍为空 → topapi/user/listadmin 取 sys_level=1    ← 企业主管理员
```

三个易错点：
- **「部门主管」不在管理员体系里**。`topapi/user/listadmin` 只返回 `sys_level` 1/2（主管理员/子管理员），
  **没有部门维度**，所以一开始会误以为钉钉没有这个角色。它在部门详情接口的
  `dept_manager_userid_list`（`String[]`，多值）里，权限是「通讯录部门信息读权限」。
- 同一个概念在钉钉三处形态不同：v2 查询返回 `String[]`、1.0 查询是 `|` 分隔字符串、
  更新接口入参是 `,` 分隔字符串。本系统只读 v2，但解析要防住字段缺失 / `null` / 空数组三态。
- 离职接口**不支持主管理员本人离职**，所以拿主管理员当操作人天然安全；反过来，
  要删的人若是主管理员，会在预检阶段就被拦下。

## 三、离职原因

- 归**被动**（`terminationReasonPassive`）。ERP 系统发起、员工本人没提交申请，按 HR 通用口径归被动；
  钉钉文档对主动/被动没有任何定义，这是本系统的口径。
- 字段**不能两个都不传**（文档明写 `passive` / `voluntary` 至少填一个），
  值是 ID，来源是 `GET https://api.dingtalk.com/v1.0/hrm/dismission/reasons` 的 `passiveList`。
- **不硬编码 ID**：官方文档没保证 ID 稳定，也没给示例值；企业的原因清单可自定义。
  取值规则：在 `passiveList` 里按名称优先级匹配 `其他` → `协议解除` → 取列表第一项；
  列表为空则抛错「未配置钉钉被动离职原因，无法执行离职」。结果缓存 24 小时。
- `dismissionMemo` 固定填 `erp系统离职流程`。

## 四、执行顺序（顺序本身是设计的一部分）

```
1. 预检所有人（任一失败 → 整批不动，OA 也不删）
     ├ 该用户是否有钉钉绑定（没有则本轮跳过钉钉，不算失败）
     ├ 钉钉侧能否查到该 userId
     ├ 是否主管理员（是则失败）
     ├ 部门主管/主管理员是否取得到（取不到则失败）
     └ 被动离职原因 ID 是否取得到（取不到则失败）
2. 逐个员工：先同步当月 + 上月考勤月报 → 再调钉钉离职
3. 离职成功后，软删该用户的 iac_account_binding 绑定记录
4. 全部成功后，OA 软删用户（沿用框架现有软删）
```

第 2 步的先后不能颠倒：`topapi/attendance/getcolumnval` 官方明确**不支持获取离职人员的考勤信息**，
人一旦离职，那个月的月报就取不到了，本地会留永久缺口。所以先落数据、再办离职。

第 3 步是必要的：绑定表设计上是「绑定后锁定，不允许改绑或解绑」，若离职后留下绑定记录，
将来同手机号重新建档时 `get_by_external_user` 会拦下来报「钉钉成员已绑定其他系统用户」，
而钉钉那边其实早没人了 —— 这是幽灵绑定。

## 五、错误处理与不可逆性

- 钉钉离职**没有撤销动作**。预检阶段能拦的都拦掉，执行阶段一旦有人失败：
  中止剩余人员、记录告警，已离职的如实上报（不做假装回滚）。
- 没绑钉钉 / 钉钉查无此人 → 跳过钉钉、不报错、OA 照删。这类人本来就没进钉钉。

## 六、与软删相关的两条

- **考勤数据在用户删除后仍可查看**：`MonthlyReportService.page()` 的 join 是
  `UserModel.id == MonthlyReportModel.oa_user_id`，不过滤 `is_deleted`，
  而框架删除是软删（行还在）。所以只要保持软删，历史考勤照常查得到，不需要额外保留策略。
  唯一隐患是将来若改物理删除，`user_name` 会取不到（它是现查的，不像 `dept_name` 有快照字段兜底）。
- **重新入职必须复活旧记录**：实测软删后按同手机号 INSERT 会撞唯一索引
  （`Duplicate entry ... for key 'sys_user.mobile'`，软删行仍在表内），
  而报错会走 `base_crud.py` 把完整 INSERT 语句吐进响应体。
  **`username` 有完全一样的坑** —— 第一次暴露出来的就是它（`Duplicate entry 'test' for key
  'sys_user.username'`），grill 时只讨论了手机号，是漏项。
  所以建档时按 `username` **或** `mobile` 命中已软删的记录，就清掉 `is_deleted` 复活它：
  刷新本次提交的字段 → 物理清掉该用户残留的钉钉绑定记录（它占着 `(system_type, mobile)` 唯一键）
  → 统一走 `bind_or_create_for_new_user` 重新绑定。撞到**未软删**的记录仍走原有「已存在」校验，
  不会误复活。

## 七、涉及的框架文件

两处都在 `app/modules/system/user/service.py`（`setting.py` 本次不动）：

- `delete()`：预检 + 逐个办钉钉离职（本条的核心）
- `create()`：`_revive_soft_deleted_user()` —— 重新入职时复活旧记录。
  这是补漏：第一轮只审了手机号，`username` 的同类坑是建档撞库时才暴露的

按 ADR-0006 的规矩单独报批后实施，批准记录写在 ADR-0006。

## 八、实测（2026-10-29 17:51）

拿测试员工（OA 用户 10 / 钉钉 `<见本机运维记录>` / <见本机运维记录>）走完整链路：

```
日志    钉钉离职完成: user=10 -> <见本机运维记录>
OA      sys_user.id=10        is_deleted=1
绑定     iac_account_binding.id=3  is_deleted=1
钉钉     按手机号查 = None；按原 userid 查 = 查不到
```

> 2026-10-29 排障：第一次删除「没有让钉钉成员离职」，原因是**新代码压根没加载** ——
> 宿主机 `uv run` 带的 StatReload 只重载了当天早些时候改 `user/model.py` 那一次，
> 之后改的 `dingtalk_client.py` / `account/service.py` / `user/service.py` 一次都没触发，
> 进程跑了三小时旧代码且无任何报错。**改完后端代码要手动重启，别指望 reload。**
> 判定代码有没有生效的可靠办法是查副作用（比如绑定记录有没有跟着软删），不是看日志有没有报错。

## 九、实测：复活逻辑（2026-10-29 18:21）

`_revive_soft_deleted_user()` 三个用例，全程在事务里跑完 `rollback`，数据库零改动：

| 用例 | 输入 | 结果 |
|---|---|---|
| A 全新用户 | `username=brandnew01` / `mobile=13800000001`（库里都没有） | 返回 `None`，走正常新建 |
| B username 命中软删 | `username=test`（= 已软删的 id=10） | 返回 `id=10`；该行 `is_deleted=0`、`deleted_time=NULL`、`name` 刷新为本次提交值；钉钉绑定 `id=4` 已被物理清除 |
| C 仅 mobile 命中软删 | `username=newguy02`（新的）/ `mobile=<见本机运维记录>`（已软删用户的） | 返回 `id=10` —— 证明 `or_` 两个入口都通 |

复核（rollback 后）：`sys_user.id=10` 仍是 `is_deleted=1`，`iac_account_binding.id=4` 仍在。

> 剩下的 `bind_or_create_for_new_user()` 是既有代码，未改动。注意测试员工在上一轮已被办离职，
> 钉钉按手机号查不到，所以真跑一次会走「创建通讯录成员」分支。
