# 订单更新走增量 diff + 更新备注日志，导入拒绝已有订单

订单数据的后续变动不再靠「重新导入覆盖」，而是新增独立的**订单更新**操作：上传最新快麦导出后，对已入库订单逐单比对子订单字段并联动刷新主订单，只改变动的行，并把源字段变动以「[时间戳] 字段 旧值→新值；」文本追加到子订单的**更新备注**列；改完按导入的聚合口径重算主订单汇总。金额四舍五入到分比较；口径之外的字段一律不动。

字段分两类。**变动即应用**的 8 个子订单字段：明细状态、已付金额、退货金额、**实退数量**、发货成本、退货成本、售后工单号、**重量kg(SKU)**——其中发货/退货成本比对的是快麦原值列（`erp_shipped_cost`/`erp_return_cost`），仅作展示同步；系统计算成本始终以 SKU 成本表为准，ERP 原值与计算值不一致时告警、不覆盖（ADR-0022）。重量原本是漏掉的：运费摊分完全按重量进行（ADR-0034），而业务上会在快麦系统里修正商品重量，刷不进来就会让摊分一直按错值算，所以纳入比对字段，变更记「重量 0.3→1.2」。**不变式校验**：实发数量（`ship_qty`）与主订单省市（`province`/`city`）——业务上已有子订单的实发数量、已有主订单的收货省市不会变，新增数量表现为新增子订单行；一旦比对发现它们变化，视同数据错误，整批中止报错。

**实退数量可变并联动重算成本**（Q30 修订，取代原「数量都不许变、系统计算成本永不重算」的口径）：更新时每条匹配到的子订单都回查 `sku_cost` 主表取当前 `cost_price`——**以系统数据库内的成本价为标准**（落点②，不是行内旧快照、更不是快麦原值），主表价与行内快照不一致即刷新该行 `cost_price`，并按新单价重算 `computed_product_cost = 成本价 × ship_qty` 与 `computed_return_cost = 成本价 × return_qty`（连发货成本一起重算，保证行内 `computed_*_cost = cost_price × 数量` 自洽；每行都回查，主表调价后跑一次更新即把历史成本拉齐）。主表 `cost_price=0` 按 0 成本照算，主表查无此 SKU 或 NULL 与导入一致（缺失、`cost_missing=True`、两成本归 0、进待补充清单）。`ship_qty` 是不变式，其变化早在中止阶段被拦，不会走到重算。

**主订单级字段静默更新**：`order_status` 变化即覆盖；`system_remark`/`seller_remark` 走**备注合并**（新空→不动、旧空且新非空→用新、旧是新子串→覆盖、否则 `旧；新` 拼接），`is_shua_order` 本轮不动（后续统一改）。主订单表**不设** `update_remark` 列——`order_status`/备注变更不写日志（拼接本身保留历史，`order_status` 变更接受无痕）。子订单 `update_remark` 只记源字段（8 个应用字段 + 成本价），派生 `computed_*_cost` 不单独记。

更新采用**两遍处理、整批原子**：第一遍只校验不写库，只要任何订单出现「库里有、新数据里没有」的子订单、任何已有子订单的实发数量变化、或任何已有主订单的省市变化，整批任何变动都不落库，接口返回错误清单。校验全过才第二遍统一应用。Excel 里多出的新子订单直接插入并记「新增子订单」；Excel 里有、库里完全没有的订单则整单创建（含店铺自动建档），子订单记「新订单，随订单更新整单创建」。

> **中止一律不留痕（2026-10-20 修订）。** 原文写的是「把中止原因记到问题子订单行的更新备注，以便事后按订单号搜回」，现已取消：任何中止原因**只在接口返回里呈现一次，不写 `update_remark`**。理由是不留痕的口径只有一条才自洽——更新通道里本来就不该混进别的发货月份的单，报出来当场处理即可；写进备注会把「更新过的订单」筛成「有更新的订单」，让 §5.1b 第 12 步的「更新状态=真正改动成功过」失真。代价：中止发生后没在页面留档，只能靠当时的报错文案。
>
> 报错文案改为**按批次号汇总**：每种批次只列样本单号与总数，形如「`order-2026-08`：300 张（示例：A001、A002、A003 …）」。原实现把命中的订单号一个个串进消息，几千张单时返回一大段几百 KB 的文本，界面读不了。

与之配套，**导入订单的语义收窄为新订单首次入库**：上传数据中只要含任何已存在的订单号，整批报错、一单不入，错误信息提示改用订单更新。原「主订单覆盖 + 子订单软删除重建」的幂等覆盖行为被移除。

**导入与更新都必须选择发货月份，月份即批次**（ADR-0033）。快麦按发货时间导出一整个月的订单，因此「同批次 = 同一发货月份维度 = 同一批订单」是业务事实而非技术约定。由此新增两条中止条件：**首次导入**时若新订单的归属月不在所选月份内，整批中止报错，提示按月份分开导；**更新**时若扫到的主订单属于其他批次，整批中止（文案见上一段，且不写备注）。目标批次若已确认，更新一律拒绝——已确认意味着利润可能已经按它算过。

> **归属月判定收紧为零容忍，且更新不新建批次（2026-10-20 修订）。**
>
> **归属月 = 一张主订单里最早那条发货时间所在的月**，按主订单判、不按子订单逐条判。跨月主订单（子订单发货时间分在两个月，快麦补发是常态）仍只算一张单，整体归**最早发货月**对应的批次；迟发的那几条跟着这张单走，不单独判定、不单独报错。
>
> 原实现允许 5% 的行级容差（`SHIP_MONTH_MISMATCH_TOLERANCE = 0.05`：归属月对不上的行占比不超过 5% 就照单全收）。这个常量**删除**，改为零容忍：一张单归属月不符就整份报错。理由——容差存在的唯一价值是「少几行别挡住整月导入」，但它同时让错月的单静默进错月批次，而那个月的利润已经按错数算过；快麦按月导出时本来就该是干净的，出现串月说明导错了，当场重来比放行便宜。顺带一提：更新通道原先**根本没有这道闸**（只有导入有），随更新新建的订单会静默挂进错月批次——更新现在走同一条判定。
>
> **更新时「该月还没批次」由自动补建改为拒绝更新**（原：该月尚无批次则自动新建一条未确认批次）。自动补建等于开了一条不经过导入窗口就能给任意月份建批次的路，与「可导入月份窗口只做界面护栏」这条口径冲突。改后必须先走导入建批次；代价是「这个月本来一张新订单都没有、只想订正老单」的场景也被挡住，只能先手工建批次或改库。
>
> 选择月份控件的窗口口径见设计文档 §5.1 第 1 步：导入弹窗给「本月往前 3 个整月、不含本月」，更新弹窗**不套窗口**（套了订正不了旧月份），接口两层都只校验格式 + 拒绝未来月。

取舍说明：更新备注选择累积文本日志而非独立结构化审计表——团队要的是在子订单行上直接看到变更历史，文本形态够用且迁移成本低，代价是无法按字段做结构化查询。整批原子（一条坏单挡住整批）而非逐单独立提交，是刻意选择「宁停勿错」：消失的子订单意味着数据源可能不完整，此时落库半截状态比全部不落更危险。导入拒绝已有订单而非跳过并报数，是为了强制「导入=新增、更新=变动」的职责边界，避免有人用导入覆盖掉更新留下的痕迹。

> **金额尺子改为「见位进分」，成本重算无条件落库，更新范围封口（2026-10-26 修订，Z1/Z2/Z3）。**
>
> 本文首段那句「金额四舍五入到分比较」作废。新口径：要落到「分」的金额，**只要小数第 3 位及以后存在任何非零数字就往上进 1 分**（正数即 `ROUND_CEILING`），恰好整到分则原样。要治的是一处历史分裂——导入把未量化的单行成本先求和、落库时由 MySQL 舍入（half away from zero，1.025→1.03），更新用 Python `.quantize(Decimal("0.01"))`（默认 ROUND_HALF_EVEN，1.025→1.02），于是同一份数据「只导入」与「导入后再更新」算出不同的钱，利润不可复现。选「见位进分」而不是把两套旧行为挑一套留下，是为了跟已经存在的运费摊分口径同构（「整票金额精确到分，余数归权重最大的那条子订单」，ADR-0034）：宁可多计一分成本、利润偏保守，也不让半分位的钱在两条路径上走两个方向。规则细节、适用范围与**不适用**范围（`cost_price` 四位列不进分、运费摊分不走这把尺）见设计文档 §15.1。**这句「首段四舍五入作废」的范围在 2026-10-29 被 AF5 收窄了一次**：见位进分只管**算出来的**金额，四个从快麦抄过来的源值列改回按四舍五入到分，见本文末尾 AF5 块与设计文档 §20.4。
>
> **主订单聚合 = Σ 已进分的子订单行**（Z2 已确认，「先加原始值再量化」废止）。原实现与模型列注释声明的「= Σ子订单」并不成立：实测单价 1.0250、两条实发 1 的子订单 → 行各 `1.03`、主订单 `2.05`。
>
> **回查主表重算出的 `computed_product_cost`/`computed_return_cost` 只要与库内值不同就写库**，不依附于同一行是否还有别的字段变化。原实现把这两列的赋值放在 `if changes:` 里面，而 `changes` 只由那 8 个源字段填——于是「主表调价了、但这 8 个字段一个没变」这一种（也是最常见的一种）情况被静默丢弃：跑更新报「成功」却把该单计入「无变化」，误差不自愈；更糟的是只改其中一条子订单的实退数量时，那条被顺手刷成新成本、另一条仍是旧值，**两条结构完全相同的子订单出现两个成本**。派生值不单独写进更新备注的口径不变。
>
> **更新触及的主订单列就此封口**（Z3=不做，2026-10-26 明确）。只有 9 列：`order_status` + `system_remark`/`seller_remark` + `buyer_paid_amount`/`refund_amount`/`refund_status`/`shipped_cost_amount`/`return_cost_amount`/`freight_income`。明确**不扩**到 `freight_cost_amount`（只由账单批次确认回写）、`is_shua_order`/`shua_status`（属刷单链路，仍挂账）、`store_id`/`platform`（建档时定）、`import_batch_id`（**永远停在首次导入的批次号**，更新不改挂）；省市仍是「变化即整批中止」，不是更新字段。

> **同一颗钉子第三次应用（2026-10-29 决议 AF1，设计文档 §20.1）。** 上面那段说「派生值只要与库内值不同就写库，不依附这一行还有别的字段变了」——前两次落地是 `computed_product_cost`/`computed_return_cost`，漏网的第三次是 **`cost_missing`**：它当时仍写在「成本价这一列碰巧变了」那个 `if` 里面。最该被看见的那一种——**库里成本价为 NULL、主表也查不到**——`NULL != NULL` 不成立，整段被跳过，`cost_missing` 保持分销翻转前的 `False`。于是这条子订单按 **0 成本**进利润，却**永远不进「待补充成本」清单**（清单就是按 `cost_missing=true` 筛的），AC 那轮只测了「有值」的翻转，这一格是漏网。
>
> 改法与 Z3 那两次不同处只在**不能无条件写**：`cost_missing` 按口径无条件**求值**，求出值与库内值**不同才写**。无条件写会让每一行都被判成「有变动」，更新结果里的「无变化 N 条」全部归零——那句话是业务方判断这份文件有没有用处的依据。口径本身一字未改（缺失 = 有主编码且取不到价，且非分销），改的是这句求值不再依附于另一列是否碰巧变了。

> **四列快麦源值改回「四舍五入到分」，见位进分只管算出来的钱（2026-10-29 决议 AF5=甲，设计文档 §20.4）。** 上面 Z1 那块把「金额四舍五入到分比较」整句作废，范围下得太宽：`paid_amount`/`refund_amount`/`erp_shipped_cost`/`erp_return_cost` 这四列是快麦报给我们的**既成事实**（顾客实付、平台实退、它自己的实发与实退成本），不是我们乘出来的钱，对它们「宁可多算一分成本」没有意义——往上进分只会把收入与退款一起虚报 1 分。新口径分两把尺：**算出来的金额**（`computed_*`、主订单成本聚合）照旧见位进分；**这四列**按四舍五入到分，导入与更新两条路径、比较与落库两个动作都用它。
>
> 决定这一条时用的实测：只读扫 `9月数据.xlsx` 的 5568 个数值，这四列**小数第 3 位全是 0**——所以两条路径此前**没有算错过一分钱**，改它治的是「以后快麦给了 3 位」和「`CONTEXT.md` 此刻写着这四列不进分、代码却在进分」这个文档与代码的互相指认。也因此**不刷存量、不重跑导入**。
>
> 三条实现约束，漏一条就把 Z1 要治的病从后门放回来：① 量化必须显式写 `ROUND_HALF_UP`——Python 默认是凑偶，而 MySQL DECIMAL 是四舍五入，两者对 1 分位的钱会走两个方向；② **比较之前先量化**，拿带 3 位的原始值直接跟库里的分精度值比，这个格子每轮都会判成「有变化」，更新备注反复写同一件事；③ 导入侧在读格子那一步就量化，`buyer_paid_amount = Σ paid_amount` 这类聚合才真的与子订单行逐字相等（Z2）。
