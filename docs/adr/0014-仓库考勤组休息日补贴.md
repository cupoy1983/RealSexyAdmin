# ADR-0014：公司休息日考勤组方案（休息 / 补工资）

- 状态：已确认，已实施并验证
- 日期：2026-11-05 建立；2026-11-06 修订
- 范围：考勤统计 → 公司休息日；薪资绩效 → 工资条生成

> 2026-11-06 修订说明：建立时补贴按「考勤组名称 == DY-仓库」匹配，而休息日重算
> 一直按 `group_id` 生效。两边键不一致时（组名快照为空、钉钉改名、历史空组名数据），
> 会出现「休息日生效、补贴算不上」的静默少发。现改为**统一按钉钉考勤组 ID 配置方案**，
> 名称快照彻底退出金额计算链路。本次修订沿用原有小节序号，不新增决策编号，
> 避免与本文及 ADR-0009 里已用的编号混淆。

## 背景

公司按「日期 + 考勤组」登记公司休息日，不同考勤组对这一天的处理不一样：

- 办公室组那天是真的休息，应出勤要相应减少；
- 仓库组那天照常上班，应出勤不减，改按天发补贴。

## 决策（建立时逐条确认，沿用原小节序号）

### 1. 不累加，按当月实际发生天数计算

补贴 = **该组当月「实际到岗」的休息日天数 × 每天补贴金额**。

不采用「每加一天就往档案上 +100」的累加写法：累加只涨不减，
跨月后金额会失控，且与当月真实天数对不上。

加一天多一份、删一天少一份，始终等于当月实际发生额。

### 2. 只进当月工资条，不进薪资档案

`iac_salary_profile.allowance`（固定补贴）保持手工设定值，**不被修改**。

补贴体现在 `iac_salary_payslip.allowance`（固定补贴快照）：
`工资条补贴 = 档案固定补贴 + 当月应发补贴天数 × money`。

档案是底薪性质的配置，休息日补贴是当月发生额，分开才能对账。

### 3. 按钉钉考勤组 ID 配置处理方案（原「按名称精确匹配」）

方案写在**后端 env 文件**里，一行 JSON，key 是钉钉考勤组 ID 的**字符串**：

```
INTERNAL_REST_DAY_POLICY={"<见本机运维记录>":{"mode":1},"330445194":{"mode":2,"money":100}}
```

| 字段 | 含义 |
|---|---|
| `mode: 1` | **休息**。登记公司休息日后按 ADR-0009 现行规则重算考勤，不发补贴，不填 `money` |
| `mode: 2` | **补工资**。登记的公司休息日照常上班，考勤统计完全不改，按 `money` 元/天发补贴 |
| `money` | 每天补贴金额，仅 `mode: 2` 必填且必须为正数 |

当前钉钉侧考勤组 ID（2026-11-06 只读核对）：`DY-OFFICE` = `<见本机运维记录>`，
`DY-仓库` = `330445194`。钉钉返回的是数字，落库是 `varchar(64)`，所以配置里写字符串。

约束：

- **没配置该 `group_id` 就不让登记公司休息日**，提示「该考勤组未配置休息日方案，请先配置再使用！」。
- **生成工资条不依赖休息日配置、不报警**：没配置的组按「没有公司休息日」算工资；要算就由管理员去 env 配好。
- `mode` 只支持 1 / 2，未知值、非法 JSON、`mode: 2` 缺 `money` 一律报错，不静默跳过。
- env 文件在进程启动时读一次（配置是常量），**改完要重启后端**；本机重启 8003，生产重启 backend 容器。配置文件由管理员自行维护。

### 4. 已生成的工资条不重算

补贴只在 `generate_month` 生成工资条时计算一次。
已生成、已确认的月份不回溯修改；本次改口径也**不回溯**历史工资条。

若休息日是在工资条生成之后才登记的，当月不会补，需要等下月或重建该月工资条。

## 补工资方案的逐天判定

补贴不是「登记条数 × 金额」，而是**逐个休息日看该员工当天的钉钉考勤原文**：

| 当天钉钉原文 | 处理 | 说明 |
|---|---|---|
| 正常 / 外勤 | 发 | 干净上班 |
| 迟到 / 早退 / 缺卡 | 发 | 人来了但有异常；缺卡仍按现行 `10 × 缺卡数²` 扣款 |
| 请假 / 旷工 | 不发 | 未出勤，且仍算请假 / 旷工，出勤少一天 |
| 钉钉休息日 / 文本为空 / 没有日明细行 | 不发 | 无有效到岗证据；属正常业务（如月中入职），不报错 |
| **程序不认识的文案** | **报错，整批生成失败** | 钉钉一般不会改返回文案；改了就必须先更新程序，不能静默算错工资 |

「程序不认识」指 `_categorize_raw()` 归到 `other` 的原文。报错信息带上月份、员工、
日期和钉钉原文，方便定位并补关键词。由于 `generate_month` 是整批原子事务，
任一员工任一天出现这种文案，**当月整批工资条都不会生成** —— 这正是「必须先改程序」
的强制效果，代价是当天发薪会被卡住。

请假或旷工那天，考勤侧重算不动统计，所以钉钉原值里的请假量、旷工量照常进入
`actual_days = 应出勤 − 旷工 − 请假`，出勤自然少一天，不会「又不上班又拿补贴」。

## 考勤侧重算的分叉

`recalc_month()` 只把「休息」方案的组放进重算日期集合：

- 「休息」方案：沿用 ADR-0009 第二节、第三节的规则表与「全月整单聚合 − 休息日占比」请假算法，
  日明细显示「公司休息」；
- 「补工资」方案与未配置的组：等同「没有公司休息日」，**不减应出勤、不清异常计数、
  不按休息日占比扣请假、日明细保留钉钉原文**，只由薪资侧按上表算补贴。

详见 ADR-0009 第八节。

## 实现位置

- `app/plugin/module_internal/config.py`：读 env、校验方案表、按 `group_id` 取方案；不改框架 `app/config/setting.py`
- `attendance/service.py`：`create_rest_days()` 登记前校验方案；`recalc_month()` 按方案过滤重算日期
- `salary/service.py`：`_rest_dates_by_group_id()` 按 ID 取当月休息日日期集合；
  `_rest_allowance()` 按当天钉钉原文逐天判定；`_calculate()` 接收补贴金额加进 `allowance`
- 已移除：按 `group_name` 统计天数、`group_name == "DY-仓库"` 判断、
  以及「按 ID 有休息日 / 按名称匹配不到」的对账报警

## 验证要点

1. 「补工资」组当月登记 3 天休息日，其中 1 天请假 → 工资条补贴 = 档案值 + 2 × money
2. 「休息」组登记 1 天休息日 → 应出勤减 1、日明细显示「公司休息」、不产生补贴
3. 未配置组即使有历史休息日记录 → 补贴 = 档案值，不报警
4. 删除 1 天休息日后重新生成 → 补贴相应减少
5. 档案 `allowance` 字段全程不变
6. 已生成月份调用 `generate_month` → 仍被 `month_generated` 拦截，不重复计算
7. 未知 `mode`、`mode: 2` 缺 `money`、非法 JSON → 明确报错；未配置组登记休息日 → 固定提示
8. 休息日那天出现程序不认识的钉钉文案 → 明确报错、不留下任何工资条；文本为空 / 无日明细行 → 正常生成、不发当天补贴

回归测试：`backend/tests/module_internal/test_rest_day_mode_policy.py`（本地造
`DY-仓库` 组绑定数据，覆盖配置解析、登记拦截、两种方案的重算差异、逐天补贴判定）。
