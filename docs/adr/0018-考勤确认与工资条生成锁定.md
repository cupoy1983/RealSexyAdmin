# ADR-0018：考勤确认与工资条生成锁定

> 状态：2026-11-10 杜总拍板并落地（复核报告功能缺陷 3）。
> 触发：复核报告功能缺陷 3 —— 工资条生成后再登记 / 删除公司休息日，会把当月考勤月报与
> 日明细重算一遍，而工资条是生成瞬间的快照，导致凭证与依据对不上、事后无法对账。
> 相关：ADR-0009（公司休息日重算）、ADR-0012（时点与通知）、ADR-0014（已生成不回溯）、
> ADR-0016（离职结算单）、`docs/项目整体复核报告-2026-11-08.md` 8.9.1 / 8.10。

## 一、杜总口径（2026-11-10）

> 工资条应该是在考勤确认后，包括公司休息日都设置好之后才可以生成的；
> 生成工资条之后，是不能修改考勤的。

结合本会话 D1 推荐（显式确认 + 生成后硬拦），落地为下面四条规定。

## 二、决定

1. **新增「考勤确认」动作**（术语见 `docs/internal/CONTEXT.md`）：管理员在确认当月公司休息日
   全部登记完毕后，显式确认该月考勤。确认按月记录，记确认人与确认时间。
   系统无法自动判断「休息日已设置好」（不知道该登记几天），所以必须由人确认。
2. **生成前第三道闸**：`generation_blockers()` 在原有「考勤全量同步」「应参与人员都有
   有效薪资档案」之外，增加「该月考勤已确认」。**未确认一律整月不生成**；
   实际只有两条生成路径共用这道闸：最后一人绩效确认后自动生成、每日任务在
   全员零绩效时自动生成（`generate_month()` 没有独立的手动生成接口）。
3. **生成后锁考勤**：`create_rest_days()` / `delete_rest_days()` 入口检查该月是否已有
   **正式工资条**，有则整批拒绝并说明月份；这一条不因撤销确认而放行。
4. **确认后也锁休息日**：已确认但未生成工资条时，要改休息日必须先**撤销确认**；
   一旦已有正式工资条，撤销确认也拒绝（防止绕过第 3 条）。

### 2026-11-10 12:19 杜总复核确认（维持现状，代码零改动）

- 顺序：**先把当月公司休息日登记、核对完毕 → 再点「确认考勤」**。系统不强制操作
  先后，但确认后要改休息日必须先撤销确认，等于把顺序倒逼出来。
- 确认后**不允许直接修改公司休息日**；「撤销确认 → 修改 → 重新确认」这条路保留。
  已生成正式工资条后，连撤销确认也拒绝，考勤彻底锁定。
- 确认后**不补拉该月考勤**：手动拉取与每月 3 日定时任务仍按「已确认／已出单」
  跳过（B2 保持现状）。
- 第 3 / 4 条与第三节的同步入口加固均为**已确认口径**，不是待清理的超范围项；
  此前助手把它们标成「自己加的、建议撤销」的判断作废。

## 三、边界与不改动项（重要）

- **离职结算单不走 `generation_blockers()`**（ADR-0016 口径）：删除员工时的结算单按
  本地已有月报出单，不受「考勤确认」影响；否则离职链会被未确认的月份卡死。
- **不拦 `sync_month()`**：该方法被每月 3 日定时任务、绩效设置时的自动补拉、
  离职前预同步共用；默认按（员工, 月份）去重，不会改写已同步月份的月报。
  在 service 内部硬拦会误伤离职链。**将来若开放 `force=True` 强制重拉入口
  （复核报告严重 5 / B1），必须同步给该入口加上「已确认 / 已生成」硬闸**——
  这是写在此处的约束，不是本轮遗漏。
- 手动同步接口 `POST /internal/attendance/sync` 走 `sync_previous_month()`，
  每月 3 日的定时任务也走它。2026-11-10 实施补记：**只靠 `can_sync` 不够** ——
  已确认月份若因人员变动（新人进考勤组）变成「未全量同步」，`can_sync` 会重新变 True，
  手动按钮和定时任务都会改写该月考勤，等于绕过第 4 条。因此：
  - `previous_month_sync_state()` 的 `can_sync` 追加 `not confirmed`；
  - `sync_previous_month()` 入口遇到「已确认 / 已有正式工资条」直接跳过并写 messages；
  - 仍然**不拦 `sync_month()` 本身**（离职前预同步、绩效设置自动补拉直接调它）。
- **不改框架文件**、不改 `response_model`；新增表在插件模块内。

## 四、数据模型与接口

- 新表 `iac_attendance_month_confirmation`：`month`（唯一）、`confirmed_at`，
  以及 `ModelMixin` / `UserMixin` 的审计字段（确认人用 `created_id`）。
  一个月份只保留一行；确认 = upsert，撤销 = 物理删除（软删会占用唯一约束）。
- `GET /internal/attendance/sync-state` 在原有 `month / synced / can_sync` 之外返回
  `confirmed / can_confirm / rest_editable`，前端据此决定按钮显隐，不新增一次请求。

  三个新字段的精确含义（2026-11-10 实施补记）：
  - `confirmed`：该月是否已确认；
  - `can_confirm`：该月「确认状态是否可变更」= 已全量同步 **且** 尚无正式工资条。
    为 false 时前端只显示状态标签、不显示确认/撤销按钮；已生成工资条的月份连撤销也拒绝，
    否则会出现「已生成工资条但显示未确认」的不一致状态。
  - `rest_editable`：`can_confirm and not confirmed`，即未确认且未生成工资条才允许改休息日。

  `sync-state` 只描述「上个月」（与绩效 / 工资条月份一致），但休息日弹窗允许选任意月份的日期。
  因此后端硬拦**不能只看 `sync-state` 返回的那一个月**：`create_rest_days()` 按 `dates` 里
  每个日期所属月份逐个检查，`delete_rest_days()` 按被删记录所属月份逐个检查。
- `POST /internal/attendance/month-confirm`（确认）、
  `DELETE /internal/attendance/month-confirm`（撤销），权限复用
  `module_internal:salary-attendance:rest`，超管放行。
- 撤销前置：该月不能有正式工资条。

### 2026-11-10 12:22 复核：保留独立表方案

杜总确认「按照你的建新表」，即保留 `iac_attendance_month_confirmation` 独立表与现有实现：
不削表、不把标记并入 `iac_attendance_monthly_report`、不撤销。本会话提出的 A 组三个备选
（A1 存储位置 / A2 是否留确认人 / A3 撤销时怎么清）**全部作废，不执行**。
代码零改动；本轮唯一剩余动作是生产环境手动执行第六节的 Alembic 迁移。

## 五、前端

考勤统计 Tab 顶部增加「确认 {month} 考勤」/「撤销确认」按钮与状态标签；
`can_confirm` 为 false 时只显示状态标签、不显示按钮（含已生成工资条的月份）。
薪资绩效 Tab 不新增操作：未确认时后端报错信息会明确提示
「请先到考勤统计页确认该月考勤」。

2026-11-10 实施补记：**不整体禁用「休息日安排」按钮**。`sync-state` 只描述上个月，
而弹窗允许选任意月份的日期，整体禁用会连其它月份的休息日也登记不了。改为：
- 弹窗内对锁定月份给出 `ElAlert` 说明；
- 保存前检查所选日期是否落在「上个月且 `rest_editable === false`」，命中则前端阻止提交并说明原因；
- 休息日列表里属于锁定月份的行禁用「删除」；
- 其它月份照常提交，**最终由后端按每个日期所属月份逐个硬拦**（只有后端知道所有月份的状态）。

## 六、生产部署

本 ADR 新增一张表，需在生产**手动执行本轮 Alembic 迁移**
（`2026_11_10_*`，down_revision = `280249fa57c2`）；本机 dev / 测试由
`init_db()` 自动建表。按既有部署流程，prod 表结构变更不走自动迁移。

## 七、被否方案

- 只做「生成后硬拦」、不加确认闸：生成前仍可能漏登记休息日，不符合杜总口径。
- 靠流程约定「3 日前登记完」、代码不加门禁：就是修复前的状态，bug 仍在。
- 在 `recalc_month()` 里统一硬拦：会拦到 `sync_month()` 末尾的幂等重算，
  进而误伤离职前预同步，故改为只在「人为修改休息日配置」的入口拦。

## 八、2026-11-11 补记：一次性数据订正不解锁考勤

第二节第 3 / 4 条「生成后锁考勤、确认后锁休息日」与第三节边界**继续生效**，本轮零改动。
ADR-0011 第十二节的一次性数据订正只改 `iac_salary_payslip` 一行的计算快照，
**不改考勤月报、不改公司休息日、不撤销或重做考勤确认**，`generation_blockers()`、
`create_rest_days()`／`delete_rest_days()` 的闸门全部保持。

订正后该月仍视为「已生成正式工资条」，锁考勤继续有效；破例只为纠正
新人入职当月全额发薪的一行，不新增「编辑工资条」接口，避免把破例变成常规能力。
订正脚本属一次性运维操作，**不纳入版本库**；执行口径与验收判据见 ADR-0011 第十二节。
